# پیاده‌سازی فاز ۲ — چرخه اشتراک و مدیریت پایه فروشگاه‌ها

> این سند وضعیت **پیاده‌سازی‌شده** محدوده فاز `PH-2` را ثبت می‌کند. تصمیم‌های قطعی کاربر با `DEC-*` در [open-decisions.md](../product/open-decisions.md) ثبت شده‌اند. پیش‌فرض‌های اجرایی این فاز با `IMP-*` و وضعیت `IMPLEMENTED_DEFAULT` مشخص شده‌اند و تصمیم قطعی کاربر نیستند.

## ۱. خلاصه اجرایی و محدوده

فاز ۲ سه قابلیت به هم پیوسته را روی زیرساخت فاز ۱ اضافه کرده است:

1. **چرخه اشتراک شرکت** بر همان مدل `company_entitlements`: `active` → `grace_period` → `read_only`، محاسبه‌شده در سرور از داده ذخیره‌شده و ساعت سرور (UTC)، بدون جدول یا وضعیت موازی.
2. **مهلت ارفاقی قابل تنظیم** با متغیر محیطی `SUBSCRIPTION_GRACE_DAYS` (پیش‌فرض ۷ روز، مقدار `0` غیرفعال‌کننده، مقادیر نامعتبر یا منفی باعث خطای راه‌اندازی).
3. **تمدید اشتراک فقط با مدیر پلتفرم** از مسیر امن و ممیزی‌شده، که بلافاصله دسترسی نوشتن را بازمی‌گرداند.
4. **مدیریت پایه فروشگاه‌ها** شامل فهرست، جزئیات، ثبت، ویرایش، فعال/غیرفعال، جست‌وجو، فیلتر، مرتب‌سازی مجاز و صفحه‌بندی سمت سرور با RLS و ایندکس.
5. **رابط کاربری فارسی و RTL** برای فهرست، جزئیات و فرم فروشگاه، با وضعیت‌های بارگذاری/خطا/خالی، اعتبارسنجی دوطرفه و هشدار روشن دوره ارفاقی/فقط‌خواندنی.
6. **مسدودسازی نوشتن در لایه مجوزدهی مشترک سرور** با کد پایدار `COMPANY_SUBSCRIPTION_READ_ONLY`؛ خواندن داده و مسیرهای هویت/امنیت/پلتفرم باز می‌مانند.

**در محدوده اجراشده:** `DEC-010` (چرخه اشتراک و فقط‌خواندنی) و `DEC-011` (محدوده فروشگاه پایه).

**خارج از محدوده و پیاده‌سازی‌نشده (طبق `DEC-011`):** GPS/نقشه/موقعیت مکانی، تشخیص تکراری، دامنه مشاهده فروشگاه برای نیروی فروش (`OD-PERM-001` باز است)، پیش‌نویس محلی فرم، کنسول کامل پلتفرم، پرداخت/صورتحساب، و هر ماژول محصول/موجودی/سفارش/تحویل/گزارش.

## ۳. Migration و مدل داده فروشگاه

`002_phase2_stores.sql` (تنها migration جدید؛ `001` دست‌نخورده):

| ستون | نوع | قاعده |
|---|---|---|
| `id` | `uuid` | کلید اصلی، `gen_random_uuid()` |
| `company_id` | `uuid` | اجباری، FK به `companies` با `ON DELETE RESTRICT` |
| `name` | `text` | اجباری، ۲ تا ۱۶۰ نویسه پس از حذف فاصله |
| `contact_name` | `text` | اختیاری، ۲ تا ۱۲۰ نویسه |
| `contact_mobile` | `text` | اختیاری، پس از نرمال‌سازی `^[+]98[0-9]{10}$` |
| `address` | `text` | اختیاری، حداکثر ۵۰۰ نویسه |
| `note` | `text` | اختیاری، حداکثر ۱۰۰۰ نویسه |
| `status` | `text` | `active` یا `inactive`، پیش‌فرض `active` |
| `created_by_user_id` / `updated_by_user_id` | `uuid` | FK به `users` با `ON DELETE SET NULL` |
| `created_at` / `updated_at` | `timestamptz` | پیش‌فرض `now()`، `updated_at` با trigger |

- **حذف:** هیچ مسیر API برای حذف فیزیکی وجود ندارد و نقش زمان اجرا مجوز `DELETE` ندارد. غیرفعال‌سازی (`status = inactive`) تنها راه کنار گذاشتن فروشگاه است؛ داده و سوابق حفظ می‌شود (`BR-STORE-004`, `IMP-018`).
- **یکتایی:** نام فروشگاه و موبایل نه در سطح شرکت و نه در سطح پلتفرم یکتا نیستند. هیچ جست‌وجوی بین‌شرکتی برای تشخیص تکراری انجام نمی‌شود (`OD-STORE-001` باز است؛ `DEC-011`).
- **ایندکس‌ها:** `(company_id, created_at DESC, id)`، `(company_id, status, created_at DESC, id)` و `(company_id, lower(name))` برای فهرست/فیلتر/صفحه‌بندی/جست‌وجو.
- **RLS:** `ENABLE` و `FORCE`؛ سیاست‌های SELECT/INSERT/UPDATE بر پایه `app.current_company_id()`؛ بدون سیاست DELETE و بدون مجوز DELETE برای `bazaria_app`.

## ۴. چرخه اشتراک و مهلت ارفاقی (`DEC-010`، `IMP-015`)

**منبع حقیقت:** `company_entitlements.valid_until` (نوع `date`) و `company_entitlements.status` به‌همراه `companies.status`. هیچ وضعیت محاسبه‌شده‌ای ذخیره نمی‌شود.

**قواعد زمانی (UTC):**

- تاریخ `valid_until` تا پایان همان روز تقویمی UTC معتبر است؛ یعنی لحظه پایان اعتبار `۰۰:۰۰ UTC` روز بعد است.
- مهلت ارفاقی از همان لحظه شروع می‌شود: `graceEndsAt = پایان روز اعتبار + SUBSCRIPTION_GRACE_DAYS × ۲۴ ساعت`.
- `active`: اکنون پیش از پایان روز اعتبار.
- `grace_period`: اکنون بین پایان اعتبار و پایان مهلت ارفاقی.
- `read_only`: اکنون در یا پس از `graceEndsAt`.
- `valid_until = null`: اشتراک بدون انقضا و `active`.
- تاریخ ناخوانا/نامعتبر: رفتار محافظه‌کارانه `read_only` (خواندن مجاز، نوشتن مسدود).
- تعلیق شرکت یا مجوز (`status ≠ active`): همان رفتار فاز ۱ با `LICENSE_INACTIVE`؛ وضعیت محاسبه‌شده `suspended` است و به هیچ عملیات شرکت (حتی خواندن) اجازه داده نمی‌شود.

**تنظیم مهلت ارفاقی:**

- متغیر `SUBSCRIPTION_GRACE_DAYS` در `.env`؛ پیش‌فرض **۷ روز** (`IMP-015`).
- `0` مهلت ارفاقی را غیرفعال می‌کند و شرکت بلافاصله پس از پایان روز اعتبار `read_only` می‌شود.
- فقط عدد صحیح نامنفی تا ۳۶۵۰ پذیرفته می‌شود؛ مقدار منفی، اعشاری یا متنی باعث خطای راه‌اندازی API می‌شود (fail fast).
- آزمون واحد، مرزهای دقیق (پایان اعتبار، پایان مهلت، صفر، تاریخ نامعتبر) و اعتبارسنجی تنظیم را پوشش می‌دهد.

**نمایش:** سرور تاریخ اعتبار (روز تقویمی) و `graceEndsAt` (لحظه UTC) را برمی‌گرداند. رابط کاربری تاریخ‌ها را شمسی و به وقت تهران نمایش می‌دهد، اما تصمیم سرور فقط بر مبنای UTC است.

## ۵. تمدید اشتراک و API مدیر پلتفرم (`IMP-017`)

- مسیر: `POST /api/v1/platform/companies/{companyId}/license/renew`
- بدنه: `{ "days": 1..3650 }` (عدد صحیح)؛ مقدار نامعتبر `422 VALIDATION_ERROR`.
- دسترسی: کوکی مستقل مدیر پلتفرم + مجوز `platform.license.manage`. نشست شرکت روی این مسیر معتبر نیست (`401 AUTH_REQUIRED`) و هیچ کاربر شرکت راهی برای تغییر تاریخ انقضا ندارد.
- محاسبه: مبنا `max(امروز UTC، valid_until فعلی)` و تاریخ جدید = مبنا + `days`؛ بنابراین تمدید پیش از انقضا زمان باقی‌مانده را حفظ می‌کند و پس از انقضا از امروز شروع می‌شود.
- محدودیت‌ها: مجوز تعلیق‌شده ابتدا باید فعال شود (`409 STATE_CONFLICT`) و مجوز بدون تاریخ انقضا نیازی به تمدید ندارد (`409 STATE_CONFLICT`).
- ممیزی: رکورد `platform.license.renewed` با مقدار قبلی/جدید و تعداد روز.
- اثر: درخواست بعدی همان نشست شرکت، وضعیت جدید را می‌بیند و نوشتن بلافاصله بازمی‌گردد؛ نیازی به ورود دوباره نیست.

## ۶. مسدودسازی نوشتن در سرور (`IMP-016`)

- **یک لایه مشترک:** در `RequestPipelineInterceptor`، پس از تأیید نشست، عضویت، زمینه شرکت و مجوز عملیات، برای هر درخواست `POST/PUT/PATCH/DELETE` شرکت‌محور وضعیت اشتراک بررسی می‌شود. هیچ endpoint فروشگاه یا شرکت بررسی تکراری ندارد و پنهان‌کردن دکمه در رابط کاربری کنترل امنیتی نیست.
- **پاسخ:** `403` با کد پایدار `COMPANY_SUBSCRIPTION_READ_ONLY`، پیام فارسی امن، `details` راهنما و `meta` شامل `subscriptionState`، `graceEndsAt` و `writeAllowed=false`. هیچ داده حساس یا داده شرکت دیگر در پاسخ نیست.
- **ممیزی/رویداد:** هر تلاش مسدودشده به‌صورت `subscription.write_blocked` ثبت می‌شود.
- **خواندن:** `GET`ها (از جمله فهرست و جزئیات فروشگاه و اطلاعات شرکت) در دوره `read_only` مجاز می‌مانند، مشروط به مجوز نقش.
- **استثناها:** ورود/خروج و تغییر/بازیابی رمز (عملیات امنیتی حساب)، و همه مسیرهای `/api/v1/platform/**` (شامل تمدید) از این سیاست مستثنا هستند. استثنای کنترلر عضویت به‌صورت صریح به عملیات دوکنترلی `PATCH /memberships/{id}` و `POST /memberships/{id}/password-reset` محدود شده است؛ افزودن عضو در حالت فقط‌خواندنی مسدود می‌ماند.
- **تعلیق:** مجوز/شرکت تعلیق‌شده همچنان با `LICENSE_INACTIVE` در لایه زمینه شرکت رد می‌شود و با اشتراک منقضی اشتباه گرفته نمی‌شود.

## ۷. API فروشگاه‌ها و قواعد اعتبارسنجی

**مسیرها (زیر `/api/v1`):**

| متد و مسیر | مجوز | توضیح |
|---|---|---|
| `GET /stores` | `store.view` | فهرست با جست‌وجو/فیلتر/مرتب‌سازی/صفحه‌بندی |
| `GET /stores/{storeId}` | `store.view` | جزئیات فروشگاه همان شرکت |
| `POST /stores` | `store.create` | ثبت فروشگاه؛ `201` و ممیزی `store.created` |
| `PATCH /stores/{storeId}` | `store.update` | ویرایش جزئی؛ بدنه خالی `422` |
| `PATCH /stores/{storeId}/status` | `store.deactivate` | فعال/غیرفعال؛ ممیزی `store.status_changed` |

**فهرست:**

- `page` از ۱، `pageSize` بین ۱ تا ۱۰۰ (پیش‌فرض ۲۰)، `q` حداکثر ۸۰ نویسه، `status` یکی از `active|inactive`، `sort` فقط `createdAt|name|updatedAt` با پیشوند اختیاری `-` (پیش‌فرض `-createdAt`) و شکستن تساوی با `id`.
- جست‌وجو روی نام، نام مسئول، نشانی و موبایل؛ موبایل ورودی نرمال‌سازی و با مقدار ذخیره‌شده مقایسه می‌شود؛ کاراکترهای `%` و `_` در ورودی escape می‌شوند.
- پاسخ: `{ data, meta }` با `page`, `pageSize`, `totalItems`, `totalPages` و `requestId`. `totalPages` برای فهرست خالی صفر است.
- هر پارامتر ناشناخته یا نامعتبر `422 VALIDATION_ERROR` می‌دهد؛ فیلدهای ناشناخته بدنه نیز رد می‌شوند.

**ایجاد/ویرایش:**

- `name` الزامی ۲ تا ۱۶۰ نویسه؛ `contactName` اختیاری ۲ تا ۱۲۰؛ `contactMobile` اختیاری و در صورت ارسال با `normalizeIranianMobile` به `+98…` تبدیل می‌شود؛ `address` حداکثر ۵۰۰؛ `note` حداکثر ۱۰۰۰.
- در ویرایش فقط فیلدهای ارسال‌شده تغییر می‌کنند؛ `null` صریح برای پاک‌کردن فیلدهای اختیاری مجاز است، اما `name` هرگز `null` نمی‌شود.
- `created_by_user_id` و `updated_by_user_id` از نشست معتبر پر می‌شوند.
- ممیزی: `store.created`، `store.updated` (قبل/بعد و فیلدهای تغییر‌یافته) و `store.status_changed` (وضعیت قبل/بعد). تغییر وضعیت به همان مقدار no-op است و ممیزی تولید نمی‌کند.

**امنیت شناسه:**

- شناسه بدشکل یا متعلق به شرکت دیگر `404 RESOURCE_NOT_FOUND` می‌دهد؛ حتی وجود یا نام فروشگاه شرکت دیگر افشا نمی‌شود.
- هدر `X-Company-Id` فقط «ادعا» است؛ عضویت، وضعیت شرکت، مجوز و وضعیت اشتراک در سرور تأیید می‌شوند. هدر جعلی شرکت دیگر `403 COMPANY_ACCESS_DENIED` می‌دهد.
- شرکت از زمینه معتبر درخواست گرفته می‌شود، نه از بدنه یا کوئری.

## ۸. مجوزها، RLS و جداسازی داده

- `ROLE_PERMISSIONS` در `packages/shared`: نقش `manager` مجوزهای `store.view`, `store.create`, `store.update`, `store.deactivate` را دارد. نقش‌های `sales_representative` و `warehouse_user` در این فاز هیچ مجوز فروشگاهی ندارند؛ `OD-PERM-001` باز است و دامنه فروش حدس زده نشده (`IMP-020`).
- مجوزها فقط از کاتالوگ مرکزی (`hasPermission`) و بدون بررسی نقش هاردکد در endpointها اعمال می‌شوند. کاربر بدون مجوز `403 PERMISSION_DENIED` می‌گیرد.
- `stores` هم‌سطح سایر جداول شرکت با `ENABLE/FORCE ROW LEVEL SECURITY` محافظت می‌شود؛ تنظیم `app.company_id` فقط پس از اثبات عضویت و به‌صورت transaction-local انجام می‌شود.
- آزمون RLS نشان می‌دهد: در زمینه شرکت A فقط رکورد A دیده می‌شود؛ `UPDATE` روی رکورد شرکت B صفر ردیف را تغییر می‌دهد؛ `INSERT` با شرکت جعلی نقض سیاست می‌دهد؛ `DELETE` با نقش زمان اجرا مجاز نیست.
- مصرف سقف فروشگاه (`IMP-019`): تعداد فروشگاه‌های فعال همان شرکت با `max_stores` مقایسه می‌شود. ثبت فروشگاه جدید یا فعال‌سازی فروشگاه غیرفعال در سقف، `403 LICENSE_STORE_LIMIT_REACHED` می‌دهد؛ غیرفعال‌سازی ظرفیت آزاد می‌کند؛ هیچ داده‌ای در کاهش سقف یا انقضا حذف نمی‌شود. برای جلوگیری از هم‌زمانی، ردیف شرکت در همان تراکنش قفل می‌شود (`FOR UPDATE`).

## ۹. رابط کاربری فارسی و RTL (`IMP-021`)

- مسیرها: `/stores` (فهرست)، `/stores/new` (ثبت) و `/stores/:storeId` (جزئیات/ویرایش) زیر همان `SessionGate` و `CompanyGate` فاز ۱؛ لینک «فروشگاه‌ها» در ناوبری فقط برای نقش دارای `store.view` نمایش داده می‌شود.
- فهرست: جست‌وجو و فیلتر وضعیت سمت سرور، جدول واکنش‌گرا با پیمایش افقی در موبایل، تعداد نتیجه، صفحه‌بندی، حالت بارگذاری، خطای قابل تلاش دوباره و حالت خالی با متن تفکیک‌شده «بدون داده» و «بدون نتیجه فیلتر».
- فرم فشرده create/edit با برچسب‌های فارسی، اعتبارسنجی سمت کاربر هم‌راستا با سرور، نگاشت خطاهای فیلد سرور، جلوگیری از ارسال دوباره و حفظ مقادیر در خطای شبکه.
- وضعیت اشتراک: در `grace_period` هشدار غیرمزاحم با تاریخ پایان مهلت؛ در `read_only` پیام روشن «شرکت در حالت فقط‌خواندنی است» به‌همراه غیرفعال‌شدن دکمه‌های افزودن/ویرایش/تغییر وضعیت/فرم‌ها. سرور مستقل از رابط کاربری، نوشتن را رد می‌کند.
- صفحه شرکت: نمایش وضعیت اشتراک، پایان مهلت ارفاقی، سقف و مصرف فروشگاه فعال، و غیرفعال‌سازی کنترل‌های نوشتن در حالت فقط‌خواندنی. بازنشانی رمز اعضا به‌عنوان عملیات امنیتی در سرور مجاز می‌ماند.
- همه برچسب‌ها فارسی، چیدمان راست‌چین و تاریخ‌ها شمسی هستند؛ اعداد با ارقام فارسی نمایش داده می‌شوند.

## ۱۰. آزمون‌ها و نتایج واقعی

| مجموعه | فرمان | نتیجه |
|---|---|---|
| API (unit + integration) | `cd apps/api && npx jest --runInBand` | **۱۲ سوئیت، ۱۰۴ آزمون، همه سبز** |
| وب | `cd apps/web && npx vitest run` | **۶ فایل، ۳۱ آزمون، همه سبز** |
| ساخت کامل | `npm run build` (ریشه) | **موفق** (shared + api + web) |
| type-check آزمون‌های API | `cd apps/api && npx tsc -p tsconfig.json --noEmit` | فقط هشدار شناخته‌شده تایپ `embedded-postgres` (وابستگی فقط‌آزمون) |

پوشش آزمون‌های فاز ۲:

- **واحد اشتراک (۷):** مرز فعال→ارفاقی، پایان دقیق مهلت→فقط‌خواندنی، مهلت صفر، نبود تاریخ انقضا، تعلیق شرکت/مجوز، تاریخ نامعتبر (fail-closed)، اعتبارسنجی تنظیم مهلت.
- **یکپارچگی اشتراک (۱۰):** نوشتن در دوره فعال و ارفاقی، خواندن مجاز و مسدودسازی همه نوشتن‌ها در فقط‌خواندنی (فروشگاه، شرکت، عضویت)، پیام/متادیتای امن خطا، رویداد امنیتی، بازماندن ورود/خروج/تغییر رمز/بازنشانی رمز عضو، بازماندن مسیرهای پلتفرم، تمدید و بازگشت فوری نوشتن، تمدید از تاریخ فعلی در صورت اعتبار باقی‌مانده، اعتبارسنجی تمدید/تعلیق/بدون‌انقضا/شناسه ناموجود، نبود مسیر تغییر انقضا برای شرکت، نفوذ با هدر جعلی/شرکت خارجی و `LICENSE_INACTIVE` برای تعلیق.
- **یکپارچگی فروشگاه (۷):** ایجاد و نرمال‌سازی موبایل + ممیزی، جداسازی فهرست و ۴۰۴ برای شناسه شرکت دیگر، هدر جعلی و نبود مجوز نقش فروش، اعتبارسنجی کوئری/بدنه/شناسه/نبود DELETE، جست‌وجو/فیلتر/مرتب‌سازی/صفحه‌بندی، ویرایش و ممیزی قبل/بعد، سقف مجوز بدون حذف داده.
- **RLS و migration:** وجود جدول و ایندکس‌ها، `ENABLE/FORCE`، جداسازی SELECT/UPDATE/INSERT و ممنوعیت DELETE برای نقش زمان اجرا.
- **وب (۳۱):** فهرست/تعداد/RTL/جدول واکنش‌گرا، حالت خالی، خطا و تلاش دوباره، ارسال جست‌وجو و فیلتر و صفحه به سرور، پنهان‌بودن اقدام‌های غیرمجاز، حالت فقط‌خواندنی و ارفاقی، سقف، اعتبارسنجی فرم، تبدیل مقادیر، جلوگیری از ارسال دوباره، حفظ مقادیر در خطای شبکه، نگاشت خطای فیلد سرور، جزئیات/ویرایش/۴۰۴.
- **رگرسیون فاز ۱:** همان سوئیت‌های قبلی (auth، membership، tenant-isolation، platform-admin، rls، migrations و آزمون‌های واحد) بدون تغییر سبز ماندند.

## ۱۱. پیکربندی و اجرای محلی

1. وابستگی‌ها: `npm install`
2. ساخت قرارداد مشترک: `npm run build -w @bazaria/shared`
3. پیکربندی: `.env` از `.env.example` و جای‌گذاری رمزهای محلی؛ برای مهلت ارفاقی `SUBSCRIPTION_GRACE_DAYS=7` (یا `0`).
4. پایگاه داده: `npm run db:start` سپس `npm run db:bootstrap`
5. Migrationها: `npm run db:migrate` (اعمال `001` و `002`؛ migration `001` تغییر نکرده است)
6. داده توسعه (اختیاری): `npm run db:seed:dev` و در صورت نیاز `npm run platform-admin:create`
7. اجرا: `npm run dev:api` و `npm run dev:web` (پورت‌های ۳۰۰۰ و ۵۱۷۳)
8. آزمون: `cd apps/api && npx jest --runInBand` و `cd apps/web && npx vitest run`

**عملیاتی:** تغییر `SUBSCRIPTION_GRACE_DAYS` نیازمند راه‌اندازی دوباره API است. مقدار نامعتبر باعث توقف راه‌اندازی می‌شود. تمدید و تغییر سقف فقط از API مدیر پلتفرم انجام می‌شود و در فاز ۲ کنسول وب پلتفرم ندارد.

## ۱۲. تصمیم‌ها، محدودیت‌ها و وضعیت Git

**پیش‌فرض‌های اجرایی این فاز:**

| شناسه | مرجع | تصمیم |
|---|---|---|
| `IMP-015` | `DEC-010`، `OD-LIC-002` | مبنای UTC، اعتبار تا پایان روز تقویمی، مهلت پیش‌فرض ۷ روز، `0` غیرفعال، بازه ۰ تا ۳۶۵۰ |
| `IMP-016` | `DEC-010` | مسدودسازی نوشتن در interceptor مشترک، استثنای هویت/امنیت/پلتفرم، خطای `COMPANY_SUBSCRIPTION_READ_ONLY` با meta امن |
| `IMP-017` | `DEC-010` | `POST /platform/companies/{id}/license/renew` با `days`، مبنا `max(امروز، انقضا)`، ممیزی `platform.license.renewed` |
| `IMP-018` | `BR-STORE-004` | بدون حذف فیزیکی و بدون مجوز DELETE؛ فقط active/inactive + RLS + ایندکس |
| `IMP-019` | `OD-STORE-003` | سقف = فروشگاه‌های فعال؛ مسدودسازی ثبت/فعال‌سازی اضافی؛ آزادسازی با غیرفعال‌سازی؛ بدون حذف داده |
| `IMP-020` | `OD-PERM-001`، `DEC-008` | مجوز فروشگاه فقط برای مدیر؛ دامنه فروش به‌عمد باز و بدون حدس |
| `IMP-021` | `DEC-010`، `DEC-011` | هشدار ارفاقی/فقط‌خواندنی، غیرفعال‌سازی کنترل‌های نوشتن، فهرست/فرم فارسی و RTL |

**تصمیم‌های باز باقی‌مانده:** `OD-PERM-001` (دامنه فروش)، `OD-STORE-001` (تشخیص تکراری)، `OD-STORE-002` (GPS؛ `DEFERRED`)، `OD-STORE-003` (گردش‌کار افزایش سقف در `PH-8`)، `OD-SEC-001` (نگهداشت ممیزی/موقعیت) و `OD-LIC-001` (پرداخت/تمدید خودکار).

**محدودیت‌های شناخته‌شده:**

- کنسول وب مدیر پلتفرم در این فاز وجود ندارد؛ تمدید و تغییر مجوز از API پلتفرم انجام می‌شود.
- هیچ UI برای ویرایش مهلت ارفاقی نیست؛ فقط تنظیم محیطی سرور.
- `GET /company` مصرف سقف را برای همه نقش‌ها برمی‌گرداند، اما تاریخ/جزئیات کامل مجوز فقط با `license.view` است.
- جست‌وجوی متنی با `ILIKE` است و جست‌وجوی فارسی پیشرفته/مترادف ندارد.
- فرم بدون پیش‌نویس محلی است (`DEC-011`)؛ در خطای شبکه، مقادیر در همان صفحه حفظ می‌شوند اما پس از بستن صفحه بازیابی نمی‌شوند.

**وضعیت Git:** هیچ commit یا push انجام نشده است. همه تغییرات فاز ۲ در working tree همان کلون/شاخه موجود هستند؛ فایل‌های جدید untracked و فایل‌های قبلی modified هستند. فهرست دقیق وضعیت باید از `git status` همان لحظه خوانده شود.
