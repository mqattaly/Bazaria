# پیاده‌سازی فاز ۱ — زیرساخت، هویت و جداسازی داده شرکت‌ها

> این سند وضعیت **پیاده‌سازی‌شده** فاز `PH-1` را ثبت می‌کند. تصمیم‌های قطعی کاربر در [open-decisions.md](../product/open-decisions.md) با شناسه `DEC-*` ثبت شده‌اند. تصمیم‌های اجرایی این فاز با `IMP-*` و وضعیت `IMPLEMENTED_DEFAULT` مشخص شده‌اند و تصمیم قطعی کاربر نیستند.

## ۱. خلاصه اجرایی و محدوده

فاز ۱ یک monorepo قابل اجرا با Frontend، Backend، پایگاه داده PostgreSQL، migration نسخه‌دار، احراز هویت کاربران شرکت و مدیر پلتفرم، عضویت چندشرکتی، نقش و مجوز پایه، اطلاعات پایه مجوز شرکت، ممیزی و رابط کاربری فارسی/RTL ایجاد کرده است.

**در محدوده اجراشده:**

- ساختار پروژه و وابستگی‌های واقعی (`DEC-007`).
- پایگاه داده، دو نقش جدا، migration و آزمون.
- ورود با موبایل و رمز عبور، نشست سمت سرور، خروج، تغییر رمز و فعال‌سازی حساب (`DEC-005`).
- ورود مستقل مدیر پلتفرم و ابزار راه‌اندازی کنترل‌شده (`DEC-009`).
- ایجاد شرکت، اطلاعات پایه، مجوز پایه و سقف فروشگاه.
- عضویت چندشرکتی، نقش مستقل در هر شرکت و انتخاب شرکت فعال (`DEC-001`).
- مجوز پایه و اجرای آن در سرور (`DEC-008`).
- جداسازی شرکت در برنامه و RLS به‌عنوان لایه دوم (`DEC-006`).
- رویدادهای امنیتی و ممیزی عملیات حساس.
- رابط کاربری ورود، فعال‌سازی، انتخاب شرکت، صفحه پایه شرکت، مدیریت اعضا برای مدیر، حساب کاربری و صفحه بدون دسترسی.

**خارج از محدوده و پیاده‌سازی‌نشده:** فروشگاه، کاتالوگ و قیمت، موجودی، سفارش، تحویل و مرجوعی، گزارش‌های کسب‌وکار، کنسول کامل پلتفرم، پرداخت و تمدید، پیامک واقعی، Offline کامل و میکروسرویس.

## ۳. معماری اجرایی و جریان درخواست

- **Modular Monolith:** سه بخش `apps/web`، `apps/api`، `packages/shared`; بدون سرویس جداگانه یا صف پیام.
- **NestJS:** ماژول‌های `DatabaseModule`، `CommonModule`، `AuthModule`، `CompanyModule`، `MembershipModule` و `PlatformModule`.
- **مسیر امنیتی مرکزی:** هر درخواست از یک interceptor عبور می‌کند:

  1. بررسی Origin برای درخواست‌های تغییردهنده (دفاع CSRF).
  2. باز کردن یک تراکنش PostgreSQL برای کل درخواست.
  3. احراز هویت (کوکی شرکت یا کوکی پلتفرم، بسته به مسیر).
  4. اعتبارسنجی زمینه شرکت از هدر `X-Company-Id` و عضویت فعال.
  5. بررسی مجوز از ماتریس نقش.
  6. اجرای کنترلر.
  7. `COMMIT` در موفقیت، `ROLLBACK` در خطا.

- **قالب موفق:** `{ "data": ..., "meta": { "requestId": "..." } }`.
- **قالب خطا:** `{ "error": { "code", "message", "details?", "requestId", "retryable" } }` مطابق [api-conventions.md](../architecture/api-conventions.md).
- **شناسه پیگیری:** مقدار معتبر `X-Request-Id` حفظ می‌شود؛ در غیر این صورت UUID تولید و در هدر پاسخ برگردانده می‌شود.
- **اعتبارسنجی:** `class-validator` با `whitelist` و `forbidNonWhitelisted`; فیلد ناشناخته (از جمله `companyId` در بدنه) رد می‌شود.
- **پایگاه داده:** `pg` Pool؛ هر درخواست یک اتصال و یک تراکنش. `DatabaseService` در نبود تراکنش از Pool استفاده می‌کند؛ در متن درخواست همیشه همان client تراکنش استفاده می‌شود.

## ۴. مدل داده و migrationها

فایل `apps/api/migrations/001_phase1_foundation.sql` تنها migration فاز است و از پایگاه داده خالی اجرا می‌شود.

| جدول | ماهیت | نکته امنیتی |
|---|---|---|
| `users` | هویت کاربر شرکت | `mobile` یکتا و E.164؛ `password_hash` اختیاری (حساب دعوت‌شده بدون رمز) |
| `sessions` | نشست کاربر شرکت | فقط `SHA-256` توکن ذخیره می‌شود؛ `revoked_at`؛ `expires_at` |
| `platform_admins` | هویت مستقل مدیر پلتفرم | بدون FK به `users`؛ بدون فلگ ارتقا روی حساب عادی |
| `platform_sessions` | نشست پلتفرم | جدول جدا؛ توکن هش‌شده |
| `password_reset_tokens` | کد فعال‌سازی/بازنشانی | تک‌مصرف؛ فقط هش؛ `used_at`؛ سازنده |
| `companies` | شرکت | `code` یکتا؛ `status` فعال/معلق؛ `currency` سه‌حرفی |
| `company_entitlements` | مجوز پایه شرکت | `status`، `max_stores`، `valid_until` |
| `company_memberships` | عضویت و نقش | یکتا `(user_id, company_id)`؛ نقش مستقل در هر شرکت |
| `audit_events` | ممیزی عملیات | بدون `UPDATE/DELETE`؛ trigger جلوگیری از تغییر |
| `security_events` | رویدادهای ورود و رد دسترسی | فقط‌افزودنی؛ خارج از مسیرهای شرکت |

**نکات:**

- همه زمان‌ها `timestamptz` هستند و نمایش شمسی/`Asia/Tehran` در لایه نمایش انجام می‌شود (`DM-PR-10`).
- `max_stores` حداقل ۱ دارد؛ در فاز ۱ فقط ذخیره و نمایش داده می‌شود. شمارش و اعمال سقف به `PH-2` و تصمیم `OD-STORE-003` وابسته است.
- `valid_until` ذخیره و نمایش داده می‌شود اما در فاز ۱ اعمال نمی‌شود (`OD-LIC-002`).
- جدول `schema_migrations` نسخه و checksum را نگه می‌دارد؛ تغییر یک migration اجراشده باعث خطای صریح می‌شود.
- migration نقش‌ها را ایجاد نمی‌کند؛ `db:bootstrap` باید قبل از `db:migrate` اجرا شود. این جداسازی عمدی است تا migration با نقش owner و اجرای برنامه با نقش runtime انجام شود.

## ۵. احراز هویت، نشست و بازیابی حساب

### کاربران شرکت (`DEC-005`)

- ورود: `POST /api/v1/auth/login` با موبایل و رمز عبور.
- نرمال‌سازی موبایل به `+989xxxxxxxxx`؛ پذیرش ارقام فارسی/عربی، `0`، `+98`، `0098`، فاصله و خط تیره.
- هش رمز: **Argon2id** با `memoryCost=19456`، `timeCost=2`، `parallelism=1` (پیش‌فرض `IMP-002`).
- سیاست رمز: حداقل ۱۰ و حداکثر ۱۲۸ نویسه، حداقل یک حرف و یک رقم، رد رمزهای رایج و رمز شامل شماره موبایل.
- پیام و کد خطای ورود برای «کاربر ناشناخته» و «رمز نادرست» یکسان است؛ زمان پاسخ با هش ساختگی یکسان‌سازی می‌شود.
- قفل: ۵ خطای متوالی برای یک شماره یا ۲۰ خطای متوالی از یک IP در پنجره ۱۵ دقیقه → `423 AUTH_ACCOUNT_LOCKED`.
- رویدادهای `auth.login.failed` و `auth.login.succeeded` در `security_events` با IP، user-agent، request-id و دلیل ثبت می‌شوند و هرگز رمز یا توکن ندارند.
- ثبت خطاهای ورود **خارج از تراکنش درخواست** انجام می‌شود تا با rollback پاسخ ناموفق از بین نرود.

### نشست (`IMP-001`)

- توکن تصادفی ۳۲ بایتی (`base64url`) در کوکی؛ فقط `SHA-256` توکن در پایگاه داده.
- کوکی: `HttpOnly`، `SameSite=Strict`، `Secure` در production، `Path=/`، بدون داده حساس.
- عمر مطلق ۱۲ ساعت؛ تمدید خودکار وجود ندارد؛ `last_used_at` حداکثر هر ۶۰ ثانیه به‌روز می‌شود.
- در هر درخواست، وجود نشست، `revoked_at`، `expires_at` و وضعیت فعال کاربر بررسی می‌شود.
- خروج: `POST /api/v1/auth/logout` نشست جاری را باطل و کوکی را پاک می‌کند.
- تغییر رمز: سایر نشست‌های کاربر باطل می‌شوند؛ نشست جاری باقی می‌ماند.
- غیرفعال‌شدن کاربر: درخواست بعدی `401 AUTH_REQUIRED`.
- غیرفعال‌شدن عضویت: درخواست بعدی `403 COMPANY_ACCESS_DENIED` برای همان شرکت؛ دسترسی به شرکت‌های دیگر حفظ می‌شود.
- تغییر نقش: در هر درخواست نقش از پایگاه داده خوانده می‌شود؛ بنابراین تغییر نقش در همان نشست و از درخواست بعدی اعمال می‌شود.

### بازیابی/فعال‌سازی (`IMP-002`، `IMP-013`)

- مدیر شرکت یا ابزار راه‌اندازی، کد یک‌بارمصرف ۳۲ بایتی با عمر ۶۰ دقیقه صادر می‌کند.
- تنها هش کد ذخیره می‌شود؛ کد فقط یک‌بار به صادرکننده نمایش داده می‌شود.
- `POST /api/v1/auth/password/set` کد را مصرف، رمز را تعیین و همه نشست‌های کاربر را باطل می‌کند.
- کد مصرف‌شده، منقضی یا نامعتبر → `400 INVALID_RESET_TOKEN` بدون افشای وضعیت حساب.
- در فاز ۱ پیامک واقعی ارسال نمی‌شود؛ تحویل کد به عهده مدیر است.

### CSRF

- `SameSite=Strict` روی کوکی‌ها.
- برای درخواست‌های `POST/PUT/PATCH/DELETE`، اگر هدر `Origin` وجود داشته باشد و در فهرست مجاز `WEB_ORIGIN`/`WEB_ORIGINS_EXTRA` نباشد، درخواست با `400 MALFORMED_REQUEST` رد و رویداد `security.origin_rejected` ثبت می‌شود.
- توکن CSRF جداگانه پیاده‌سازی نشده است؛ این تصمیم در `IMP-001` مستند شده و در صورت نیاز به الگوی `double-submit` قابل افزودن است.
- در `NODE_ENV=development` علاوه بر فهرست پیکربندی‌شده، `localhost`/`127.0.0.1` و دامنه پیش‌نمایش `*.e2b.app` هم پذیرفته می‌شوند تا UI از طریق proxy همان‌مبدأ کار کند؛ در `production` تنها `WEB_ORIGIN`/`WEB_ORIGINS_EXTRA` مجاز است.

## ۶. جداسازی داده شرکت‌ها و RLS (`DEC-006`، `IMP-005`)

**لایه برنامه (الزام اصلی):**

- هدر `X-Company-Id` فقط ادعاست.
- سرور عضویت فعال کاربر در آن شرکت را از پایگاه داده می‌خواند؛ نبود عضویت → `403 COMPANY_ACCESS_DENIED`.
- سپس وضعیت شرکت و مجوز فعال بررسی می‌شود؛ تعلیق → `403 LICENSE_INACTIVE`.
- فقط پس از این بررسی‌ها، زمینه شرکت در تراکنش تنظیم می‌شود.
- نقش مجوز از همان عضویت گرفته می‌شود؛ نه از بدنه، هدر یا کلاینت.
- همه endpointهای شرکتی بدون استثنا مجوز صریح یا `@CompanyScoped` دارند؛ فراموشی این decorator به نبود زمینه و صفر رکورد منجر می‌شود، نه افشا.

**لایه پایگاه داده (دفاع دوم):**

- `ENABLE ROW LEVEL SECURITY` و `FORCE ROW LEVEL SECURITY` روی `companies`، `company_entitlements`، `company_memberships` و `audit_events`.
- زمینه با `set_config('app.company_id', ..., true)`، `app.user_id` و `app.platform_admin`؛ همه transaction-local.
- پس از `COMMIT` یا `ROLLBACK`، تنظیمات پاک می‌شوند؛ آزمون pool reuse و rollback این را ثابت می‌کند.
- نقش runtime `bazaria_app`: بدون `SUPERUSER`، `CREATEDB`، `CREATEROLE`، `BYPASSRLS` و بدون مالکیت جدول.
- نقش migration `bazaria_owner`: DDL و مالکیت؛ با `FORCE RLS` حتی owner نیز بدون policy رکورد نمی‌بیند.
- `audit_events` هیچ grant ویرایش/حذف ندارد و trigger فقط‌افزودنی بودن را تضمین می‌کند.
- `security_events` و جدول‌های هویت سطح پلتفرم هستند و RLS شرکت‌محور ندارند؛ مسیر API برای خواندن آن‌ها وجود ندارد.

**آزمون‌های RLS:** بدون زمینه صفر رکورد؛ زمینه شرکت A فقط A؛ تلاش برای به‌روزرسانی شرکت B صفر رکورد؛ درج ممیزی برای شرکت B رد می‌شود؛ نقش owner نیز بدون policy صفر رکورد می‌بیند؛ نقش runtime نمی‌تواند جدول بسازد.

## ۷. جداسازی مدیر پلتفرم (`DEC-009`، `IMP-006`)

| موضوع | پیاده‌سازی |
|---|---|
| هویت | جدول `platform_admins`، بدون FK به `users` و بدون فلگ ارتقا |
| نشست | جدول `platform_sessions` و کوکی `bz_platform_session` |
| مسیر کوکی | `Path=/api/v1/platform` تا مرورگر آن را به مسیرهای شرکت نفرستد |

| سیاست | endpointهای پلتفرم فقط کوکی پلتفرم را می‌پذیرند؛ کوکی شرکت → `401` |
| مسیر شرکت | کوکی پلتفرم روی `/api/v1/company` یا `/api/v1/me` پذیرفته نمی‌شود |
| راه‌اندازی | `npm run platform-admin:create -- --username ... --name ...` با رمز از `PLATFORM_ADMIN_PASSWORD` یا تولید یک‌باره |
| رمز پیش‌فرض | وجود ندارد؛ هیچ secret در مخزن نیست |
| endpoint ارتقا | وجود ندارد |
| ممیزی | ایجاد شرکت و تغییر مجوز شرکت با `actor_type=platform_admin` ثبت می‌شود |
| دسترسی به داده شرکت | پیش‌فرض ندارد؛ مسیر شرکت با نشست پلتفرم کار نمی‌کند (`OD-PERM-003` باز برای پشتیبانی) |

- API خواندن ممیزی در فاز ۱ وجود ندارد (`IMP-011`).

- احراز هویت: ورود موفق، کوکی hardened، پیام یکسان خطا، قفل پس از خطاهای متوالی، خروج و ابطال، رد توکن جعلی، مصرف یک‌باره کد، ابطال نشست‌های قبلی، سیاست رمز، رد فیلد ناشناخته، شناسه درخواست.

- چندشرکتی: فهرست شرکت‌ها با نقش هر شرکت، انتخاب شرکت، جعل `X-Company-Id`، نبود هدر، UUID نامعتبر، مرز نقش بین دو شرکت، محدودیت انبار، غیرفعال‌سازی فوری عضویت/کاربر، تعلیق شرکت/مجوز، ممیزی تغییر شرکت.
- عضویت: افزودن کاربر جدید، کد یک‌بارمصرف بدون ذخیره متن ساده، جلوگیری از تکرار، فعال‌سازی حساب دعوت‌شده، تغییر نقش و اثر فوری، ممنوعیت تغییر نقش خود، غیرفعال‌سازی و ممیزی، بازنشانی رمز و ابطال نشست.
- پلتفرم: کوکی جدا و `Path` محدود، عدم استفاده متقابل نشست‌ها، ایجاد شرکت + مجوز + مدیر نخست، کد تکراری، فهرست و تغییر مجوز با ممیزی، قفل ورود، نبود مسیر ارتقا.
- RLS: حداقل‌امتیاز بودن نقش runtime، `ENABLE/FORCE` روی چهار جدول، صفر رکورد بدون زمینه، فیلتر شرکت، عدم نشت پس از commit/rollback/pool reuse، پنهان‌ماندن عضویت سایر کاربران، جلوگیری از به‌روزرسانی/درج بین‌شرکتی، دسترسی پلتفرم، اطلاع‌نداشتن owner از رکوردها، فقط‌افزودنی بودن ممیزی.
- Migration: اجرای دوباره بدون تغییر، اجرا روی پایگاه داده خالی، تشخیص تغییر checksum، وجود جدول‌ها و `FORCE RLS`.

هیچ آزمونی برای سبز شدن تضعیف نشد؛ RLS، بررسی عضویت و مجوزها دست‌نخورده‌اند.

## ۱۲. راه‌اندازی، پیکربندی و عملیات

### پیش‌نیاز

- Node.js 20.19+ (در محیط آزمون: 22).
- PostgreSQL 14+ در محیط واقعی؛ در این محیط توسعه، PostgreSQL 18.4 از بسته `embedded-postgres` اجرا می‌شود.
- Docker لازم نیست.

### متغیرهای محیطی

`.env.example` فقط نام متغیرها و جای‌نگهدارهای غیرحساس (`YOUR_*`) دارد؛ پیش از اجرا باید جایگزین شوند. `npm run db:start` رمز سوپریوزر را از `DATABASE_ADMIN_URL` می‌خواند و هیچ رمز ثابتی در مخزن وجود ندارد. متغیرهای اصلی:

- `DATABASE_ADMIN_URL` (فقط bootstrap/آزمون)، `DATABASE_OWNER_URL` (migration)، `DATABASE_URL` (runtime).
- `DB_OWNER_PASSWORD`، `DB_APP_PASSWORD` (حداقل ۱۲ نویسه).
- `WEB_ORIGIN` / `WEB_ORIGINS_EXTRA` برای CORS/Origin.
- `SESSION_TTL_HOURS`، `LOGIN_WINDOW_MINUTES`، `LOGIN_MAX_FAILURES_PHONE`، `LOGIN_MAX_FAILURES_IP`، `COOKIE_SECURE`.

### ترتیب راه‌اندازی

```bash
npm install
cp .env.example .env
npm run db:start                 # پنجره جدا؛ PostgreSQL روی 5433
npm run db:bootstrap             # نقش bazaria_owner و bazaria_app + پایگاه داده
npm run db:migrate
npm run db:seed:dev              # داده نمایشی؛ رمز یک‌بار چاپ می‌شود
npm run platform-admin:create -- --username admin --name "مدیر پلتفرم"
npm run dev                      # API :3000، وب :5173
```

`dev` برای API از `tsc-watch` استفاده می‌کند (نه tsx/esbuild) تا metadata تزریق وابستگی NestJS حفظ شود؛ با `tsx` وابستگی‌های constructor تزریق نمی‌شدند.

### ابزارهای راه‌اندازی

| فرمان | کاربرد |
|---|---|
| `npm run db:bootstrap` | ایجاد/به‌روزرسانی نقش‌ها و پایگاه داده با حداقل امتیاز |
| `npm run db:migrate` | اجرای migrationهای نسخه‌دار با نقش owner |
| `npm run db:seed:dev` | داده نمونه توسعه؛ در production اجرا نمی‌شود؛ رمز تصادفی یک‌باره |
| `npm run user:create -- --mobile ... --name "..."` | ساخت کاربر بدون رمز + کد فعال‌سازی |
| `npm run membership:grant -- --mobile ... --company CODE --role manager` | اتصال کاربر موجود به شرکت (بازیابی/راه‌اندازی) |
| `npm run platform-admin:create -- --username ... --name "..."` | نخستین مدیر پلتفرم؛ رمز از env یا تولید یک‌باره |

### تولید

- `NODE_ENV=production` و `COOKIE_SECURE=true`.
- `DATABASE_URL` باید نقش runtime باشد؛ نقش owner فقط برای migration.
- `DATABASE_ADMIN_URL` را در محیط اجرا قرار ندهید.
- پشت HTTPS و reverse proxy با همان origin وب اجرا شود؛ در غیر این صورت `WEB_ORIGIN` را دقیق تنظیم کنید.
