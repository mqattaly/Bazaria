# قراردادهای API — بازاریا

| مورد | مقدار |
|---|---|
| نسخه سند | 0.1 — فاز صفر |
| وضعیت | پیشنهادی — نیازمند تأیید کاربر |
| دامنه | قرارداد ارتباط Frontend و Backend و مصرف‌کنندگان آینده |
| اسناد مرتبط | [PRD](../product/product-requirements.md) · [مدل داده](data-model.md) · [امنیت](security-and-permissions.md) · [معماری](system-architecture.md) |

> **هشدار:** این سند فقط قرارداد را توصیف می‌کند. هیچ فایل OpenAPI، نمونه اجرایی، کلاینت یا endpointی در این فاز ایجاد نشده است. نمونه‌های JSON صرفاً توضیحی‌اند و داده آن‌ها ساختگی و غیرحساس است.
>
> تصمیم‌هایی که هنوز نهایی نیستند با `OD-*` یا برچسب «نیازمند تصمیم» مشخص شده‌اند.

## ۱. اصول کلی

| شناسه | اصل |
|---|---|

| `API-PR-02` | نام منابع جمع و با حروف کوچک و خط تیره؛ عملیات با متد HTTP بیان می‌شود. |

| `API-PR-09` | همه پاسخ‌ها شناسه پیگیری درخواست دارند. |
| `API-PR-10` | تغییرات ناسازگار در فیلدهای درخواست مجاز نیست؛ افزودن فیلد اختیاری در پاسخ مجاز است. |

## ۲. نسخه‌بندی مسیرها

- پیشوند نسخه: `/api/v1`
- مسیرهای دامنه شرکت: `/api/v1/{resource}`
- مسیرهای سطح پلتفرم: `/api/v1/platform/{resource}`

| قاعده | توضیح |
|---|---|
| نسخه در مسیر | نسخه اصلی در مسیر قرار می‌گیرد (`v1`, `v2`). |
| تغییر سازگار | افزودن فیلد اختیاری، افزودن مقدار جدید به یک شمارشی با احتیاط، افزودن endpoint جدید؛ بدون تغییر نسخه. |
| تغییر شکننده | حذف یا تغییر معنای فیلد، تغییر نوع داده، تغییر قالب خطا، تغییر معنای کد خطا؛ فقط با نسخه جدید. |
| معیار نسخه جدید | وجود مصرف‌کننده مستقل (اپ موبایل یا یکپارچگی بیرونی) یا نیاز به تغییر غیرسازگار. |
| دوره پشتیبانی نسخه قدیم | نیازمند تصمیم در زمان انتشار نسخه دوم؛ در این سند عدد تعیین نمی‌شود. |
| مستندسازی | تولید مستند OpenAPI در فاز پیاده‌سازی پیشنهاد می‌شود (`ARCH-P-004`). |

## ۳. نام‌گذاری endpointها

| الگو | نمونه | توضیح |
|---|---|---|
| فهرست | `GET /api/v1/stores` | با صفحه‌بندی و فیلتر |
| جزئیات | `GET /api/v1/stores/{storeId}` | شناسه در مسیر |
| ایجاد | `POST /api/v1/stores` | پاسخ شامل شناسه و محل منبع |
| ویرایش کامل | `PUT /api/v1/stores/{storeId}` | فقط اگر جایگزینی کامل منطقی باشد |
| ویرایش جزئی | `PATCH /api/v1/stores/{storeId}` | پیشنهاد برای اکثر ویرایش‌ها |
| زیرمنبع | `GET /api/v1/orders/{orderId}/items` | رابطه مالکیتی روشن |
| گذار وضعیت | `POST /api/v1/orders/{orderId}/confirm` | عملیات دامنه‌ای، نه ویرایش فیلد |
| لغو | `POST /api/v1/orders/{orderId}/cancel` | با بدنه دلیل |
| تأیید موجودیت | `POST /api/v1/returns/{returnId}/approve` | با مجوز و ممیزی |

**قواعد نام‌گذاری:**

- نام منابع جمع، انگلیسی، `kebab-case`.
- شناسه‌ها در مسیر با نام موجودیت و پسوند `Id` در مستندات (`{storeId}`).
- افعال در مسیر فقط برای عملیات دامنه‌ای مجاز است (`confirm`, `cancel`, `approve`, `ship`, `deliver`)، نه برای CRUD.
- نام فیلدها در بدنه و پاسخ، `camelCase` است.
- مسیرهای سطح پلتفرم هرگز زیر مسیر شرکت قرار نمی‌گیرند.

**نمونه مسیرهای پیشنهادی (فقط طرح، نه پیاده‌سازی):**

| ماژول | مسیرها |
|---|---|
| هویت | `POST /api/v1/auth/login`، `POST /api/v1/auth/logout`، `GET /api/v1/me`، `GET /api/v1/me/companies` |
| شرکت | `GET /api/v1/company`، `PATCH /api/v1/company` |
| عضویت | `GET /api/v1/memberships`، `POST /api/v1/memberships`، `PATCH /api/v1/memberships/{membershipId}` |
| مجوز | `GET /api/v1/license`، `GET /api/v1/license/usage` |
| فروشگاه | `GET/POST /api/v1/stores`، `GET/PATCH /api/v1/stores/{storeId}`، `POST /api/v1/stores/duplicate-checks` |
| کاتالوگ | `GET/POST /api/v1/products`، `GET/PATCH /api/v1/products/{productId}`، `POST /api/v1/products/{productId}/prices` |
| انبار | `GET /api/v1/inventory`، `GET /api/v1/inventory/{productId}/movements`، `POST /api/v1/inventory/adjustments` |
| سفارش | `GET/POST /api/v1/orders`، `GET/PATCH /api/v1/orders/{orderId}`، `POST /api/v1/orders/{orderId}/confirm`، `POST /api/v1/orders/{orderId}/cancel` |
| توزیع | `POST /api/v1/shipments`، `POST /api/v1/shipments/{shipmentId}/ship`، `POST /api/v1/deliveries`، `POST /api/v1/returns`، `POST /api/v1/returns/{returnId}/approve` |
| گزارش | `GET /api/v1/reports/sales`، `GET /api/v1/reports/orders`، `GET /api/v1/reports/inventory`، `GET /api/v1/reports/users` |
| پلتفرم | `GET/POST /api/v1/platform/companies`، `PATCH /api/v1/platform/companies/{companyId}/license` |

> این مسیرها پیشنهادی هستند. هر تغییر در نام یا ساختار مسیر پس از تثبیت در فاز، تغییر قرارداد مشترک محسوب می‌شود و باید اثر آن بر فازهای قبلی بررسی شود.

### ۳.۱. مسیرهای پیاده‌سازی‌شده در `PH-2`

| متد و مسیر | دسترسی | توضیح |
|---|---|---|
| `GET /api/v1/stores` | `store.view` | `page`, `pageSize` (۱ تا ۱۰۰)، `q`، `status`، `sort` (`createdAt|name|updatedAt` با `-`) |
| `GET /api/v1/stores/{storeId}` | `store.view` | شناسه خارج از شرکت `404` بدون افشا |
| `POST /api/v1/stores` | `store.create` | `201`، ممیزی `store.created`، کنترل سقف مجوز |
| `PATCH /api/v1/stores/{storeId}` | `store.update` | بدنه خالی `422`، ممیزی قبل/بعد |
| `PATCH /api/v1/stores/{storeId}/status` | `store.deactivate` | `{ "status": "active|inactive" }` |
| `POST /api/v1/platform/companies/{companyId}/license/renew` | `platform.license.manage` | `{ "days": 1..3650 }`، ممیزی `platform.license.renewed` |

- `POST /api/v1/stores/duplicate-checks` در این فاز پیاده‌سازی نشده است (`OD-STORE-001` باز)؛ هیچ جست‌وجوی بین‌شرکتی برای تشخیص تکراری وجود ندارد.
- `GET /api/v1/company` علاوه بر اطلاعات پایه، `subscription` (وضعیت محاسبه‌شده) و `storeUsage` (`active`, `limit`) را برمی‌گرداند. `GET /api/v1/license` همین وضعیت را با جزئیات مجوز دارد.
- همه نوشتن‌های شرکت‌محور در `read_only` با `COMPANY_SUBSCRIPTION_READ_ONLY` (403) رد می‌شوند؛ استثناها در [security-and-permissions.md](security-and-permissions.md) §۳.۵ آمده‌اند.
- فیلدهای ناشناخته در کوئری و بدنه با `422 VALIDATION_ERROR` رد می‌شوند (whitelist سخت‌گیرانه).

## ۴. ساختار درخواست و پاسخ

### ۴.۱. هدرهای استاندارد درخواست

| هدر | الزام | توضیح |
|---|---|---|
| `Content-Type` | برای بدنه | `application/json` |
| `Accept` | توصیه‌شده | `application/json` |
| `X-Company-Id` | برای مسیرهای دامنه شرکت | شرکت فعال؛ **فقط ادعا**، در سرور اعتبارسنجی می‌شود |
| `Idempotency-Key` | برای عملیات حساس | شناسه یکتای درخواست |
| `If-Match` | اختیاری | نسخه رکورد برای جلوگیری از تعارض هم‌زمانی |
| `X-Request-Id` | اختیاری | شناسه پیگیری؛ در صورت نبود، سرور تولید می‌کند |
| `Accept-Language` | اختیاری | زبان پیام‌ها؛ پیش‌فرض فارسی |

**انتخاب محل انتقال شرکت فعال:** هدر `X-Company-Id` انتخاب و در فاز ۱ پیاده‌سازی شد (`DEC-006`، `IMP-014`)؛ زیرا شرکت زمینه درخواست است، نه بخشی از شناسه منبع. تغییر این قرارداد پس از تثبیت شکننده محسوب می‌شود.

**اعتبارسنجی شرکت فعال:** اگر هدر ارسال نشود → خطای `COMPANY_CONTEXT_REQUIRED`. اگر کاربر در آن شرکت عضو نباشد → خطای `COMPANY_ACCESS_DENIED` بدون افشای وجود داده. مسیرهای `/me` و `/platform` از این قاعده مستثنا هستند.

### ۴.۲. قالب پاسخ موفق

```json
{
  "data": {
    "id": "st_example_001",
    "name": "فروشگاه نمونه",
    "status": "active"
  },
  "meta": {
    "requestId": "req_example_001"
  }
}
```

- `data` برای یک منبع: شیء؛ برای فهرست: آرایه.
- `meta` شامل شناسه درخواست و اطلاعات صفحه‌بندی است.
- پاسخ موفق بدون بدنه (`204`) فقط برای حذف/غیرفعال‌سازی مجاز است و همچنان `requestId` را در هدر `X-Request-Id` برمی‌گرداند.

### ۴.۳. قالب فهرست و صفحه‌بندی

```json
{
  "data": [
    { "id": "ord_example_001", "status": "pending_approval" },
    { "id": "ord_example_002", "status": "confirmed" }
  ],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 2,
    "totalPages": 1,
    "requestId": "req_example_002"
  }
}
```

| موضوع | قرارداد پیشنهادی |
|---|---|
| پارامترهای صفحه‌بندی | `page` (از ۱) و `pageSize` |
| مقدار پیش‌فرض و سقف | پیشنهاد: پیش‌فرض ۲۰ و سقف ۱۰۰؛ مقدار نهایی نیازمند تأیید |
| نوع دوم صفحه‌بندی | برای فهرست‌های بزرگ و پویا، `cursor` و `limit` با `nextCursor` در `meta` |
| مرتب‌سازی | `sort=createdAt` یا `sort=-createdAt` (منفی = نزولی)؛ فقط فیلدهای مجاز |
| جست‌وجو | `q=` با حداقل طول مشخص و نرمال‌سازی فارسی |
| فیلتر | پارامترهای صریح مانند `status=confirmed`، `storeId=...` |
| فیلتر زمانی | `createdFrom` و `createdTo` |
| رفتار پارامتر نامعتبر | خطای اعتبارسنجی، نه نادیده گرفتن بی‌صدا |
| فهرست سفارش پیش‌فرض | پیشنهاد: جدیدترین‌ها اول |

### ۴.۴. قالب خطا

```json
{
  "error": {
    "code": "STOCK_INSUFFICIENT",
    "message": "موجودی کافی برای این محصول وجود ندارد.",
    "details": [
      {
        "field": "items[0].quantity",
        "code": "QUANTITY_EXCEEDS_AVAILABLE",
        "message": "مقدار درخواستی از موجودی قابل‌استفاده بیشتر است."
      }
    ],
    "requestId": "req_example_003",
    "retryable": false
  }
}
```

| فیلد | قاعده |
|---|---|
| `code` | کد پایدار و ماشین‌خوان، تغییرناپذیر؛ پیام فارسی از آن مشتق می‌شود |
| `message` | پیام کوتاه فارسی برای نمایش؛ هرگز متن خام استثنا نیست |
| `details` | اختیاری؛ فهرست خطاهای فیلد یا علت‌های قابل‌اقدام |
| `requestId` | برای پیگیری پشتیبانی |
| `retryable` | آیا تلاش مجدد منطقی است (بدون تضمین موفقیت) |
| `meta` | جایگزین اطلاعات تکمیلی؛ نباید داده حساس داشته باشد |

**قواعد پیام خطا:**

- پیام فارسی، کوتاه و قابل‌اقدام.
- خطای مربوط به موجودی باید مقدار یا علت را بدون افشای داده شرکت دیگر توضیح دهد.
- خطای مجوز نباید تأیید کند رکورد وجود دارد یا ندارد.
- متن استثنای پایگاه داده و پشته خطا هرگز نمایش داده نمی‌شود.

### ۴.۵. کدهای خطای پایدار

| کد | HTTP | معنا | قابل تلاش مجدد |
|---|---|---|---|
| `VALIDATION_ERROR` | 422 | ورودی نامعتبر | خیر تا اصلاح |
| `MALFORMED_REQUEST` | 400 | ساختار درخواست نامعتبر | خیر |
| `COMPANY_CONTEXT_REQUIRED` | 400 | شرکت فعال ارسال نشده | خیر تا اصلاح |
| `AUTH_REQUIRED` | 401 | نشست وجود ندارد یا منقضی شده | پس از ورود |
| `AUTH_INVALID_CREDENTIALS` | 401 | اعتبارنامه نادرست | پس از اصلاح |
| `AUTH_ACCOUNT_LOCKED` | 423 | حساب موقتاً قفل است | بعداً |
| `COMPANY_ACCESS_DENIED` | 403 | عضویت یا دسترسی به شرکت وجود ندارد | خیر |
| `PERMISSION_DENIED` | 403 | مجوز عملیات وجود ندارد | خیر |
| `RESOURCE_NOT_FOUND` | 404 | منبع در محدوده مجاز یافت نشد | خیر |
| `STATE_CONFLICT` | 409 | گذار وضعیت نامجاز یا تغییر هم‌زمان | گاهی |
| `STALE_VERSION` | 409 | نسخه رکورد قدیمی است | پس از بازخوانی |
| `STOCK_INSUFFICIENT` | 409 | موجودی قابل‌استفاده کافی نیست | پس از تغییر مقدار |
| `RESERVATION_CONFLICT` | 409 | تعارض رزرو هم‌زمان | گاهی |
| `IDEMPOTENCY_KEY_REUSED` | 409 | همان کلید با محتوای متفاوت | خیر |
| `ORDER_NOT_CANCELLABLE` | 409 | سفارش در وضعیت قابل لغو نیست | خیر |
| `LICENSE_STORE_LIMIT_REACHED` | 403 | سقف فروشگاه مجاز تکمیل شده | پس از تغییر مجوز |
| `LICENSE_INACTIVE` | 403 | مجوز شرکت فعال نیست | پس از تمدید |
| `COMPANY_SUBSCRIPTION_READ_ONLY` | 403 | مهلت ارفاقی اشتراک پایان یافته و نوشتن مجاز نیست | پس از تمدید |
| `RATE_LIMITED` | 429 | تعداد درخواست بیش از حد | بعداً |
| `INTERNAL_ERROR` | 500 | خطای پیش‌بینی‌نشده | گاهی |
| `SERVICE_UNAVAILABLE` | 503 | سرویس موقتاً در دسترس نیست | بله |

**قاعده:** کدهای خطا بخشی از قرارداد عمومی هستند. تغییر معنا یا حذف کد، تغییر شکننده است. افزودن کد جدید مجاز است، اما کلاینت‌ها باید کد ناشناخته را به‌صورت عمومی مدیریت کنند.

**کدهای افزوده در فاز ۲:** `COMPANY_SUBSCRIPTION_READ_ONLY` (403) و `LICENSE_STORE_LIMIT_REACHED` (403، از قبل رزرو شده بود). `COMPANY_SUBSCRIPTION_READ_ONLY` شامل `meta` غیرحساس `subscriptionState`, `graceEndsAt`, `writeAllowed` و `details` راهنمای تمدید است.

**کدهای افزوده در فاز ۱** (بدون تغییر معنای کدهای بالا): `MEMBERSHIP_EXISTS` (409)، `COMPANY_CODE_TAKEN` (409)، `SELF_MANAGEMENT_FORBIDDEN` (403)، `LAST_MANAGER_REQUIRED` (409)، `PASSWORD_POLICY_VIOLATION` (422)، `INVALID_RESET_TOKEN` (400). فهرست اجرایی در `packages/shared/src/index.ts` است.

## ۵. اعتبارسنجی ورودی

| موضوع | قاعده پیشنهادی |
|---|---|
| منبع حقیقت | اعتبارسنجی سرور؛ اعتبارسنجی کلاینت فقط تجربه کاربری |
| فیلدهای ناشناخته | **رد** درخواست با `VALIDATION_ERROR` (جلوگیری از تزریق ناخواسته فیلد) |
| فیلدهای الزامی | بررسی صریح و پیام در محل فیلد |
| رشته‌ها | حذف فاصله اضافی، محدودیت طول، رد کاراکترهای کنترلی |
| شماره تماس | نرمال‌سازی و اعتبارسنجی قالب پیش از ذخیره؛ نمایش قالب فارسی |
| شناسه‌ها | قالب مشخص و بررسی تعلق به شرکت جاری |
| اعداد | بدون تبدیل خودکار نوع؛ رشته عددی نامعتبر رد می‌شود |
| تاریخ‌ها | قالب استاندارد و بازه معتبر؛ تاریخ آینده در فیلدهای گذشته ممنوع |
| شمارشی‌ها | فقط مقادیر مجاز؛ مقدار ناشناخته رد می‌شود |
| بدنه بزرگ | محدودیت اندازه بدنه؛ درخواست بزرگ‌تر رد می‌شود |
| پیام خطا | اشاره به نام فیلد مسیر (مثل `items[0].quantity`) و علت |

**اعتبارسنجی کسب‌وکاری** (مثلاً موجودی کافی، محصول فعال، سقف مجوز) جدا از اعتبارسنجی ساختاری است و در لایه دامنه انجام می‌شود؛ خطای آن با کد دامنه‌ای مشخص برمی‌گردد.

## ۶. احراز هویت و مجوزدهی

| موضوع | قرارداد پیشنهادی | وضعیت |
|---|---|---|
| روش احراز هویت | نشست مبتنی بر کوکی امن `HttpOnly` (توکن فقط سمت سرور، هش‌شده) | تأییدشده (`DEC-005`، `IMP-001`) |
| حفاظت CSRF | `SameSite=Strict` + بررسی Origin برای درخواست‌های تغییردهنده | پیاده‌سازی‌شده (`IMP-001`) |
| عمر نشست و تمدید | ۱۲ ساعت مطلق، بدون تمدید خودکار | پیش‌فرض (`IMP-001`؛ `OD-AUTH-003` باز) |
| بررسی هویت | در هر درخواست، پیش از هر منطق دامنه | پیشنهادی |
| بررسی عضویت شرکت | از روی `X-Company-Id` و عضویت فعال | الزامی |
| بررسی مجوز | بر اساس نقش/مجوز در همان شرکت | الزامی |
| بررسی سطح رکورد | محدوده مشاهده (مثلاً فروشگاه‌های مجاز) | وابسته به `OD-PERM-001` |
| مسیرهای پلتفرم | هویت مدیر پلتفرم جدا؛ بدون زمینه شرکت | الزامی |
| پاسخ خطا | `401` برای نبود هویت، `403` برای نبود مجوز، بدون افشای وجود رکورد | الزامی |
| خروج و ابطال | ابطال نشست جاری و امکان ابطال نشست‌های کاربر غیرفعال‌شده | الزامی |

**قاعده طلایی:** هیچ endpointی نباید به `companyId` ارسالی به‌عنوان منبع حقیقت تکیه کند. شرکت از عضویت معتبر کاربر استخراج و سپس با زمینه درخواست تطبیق داده می‌شود (`BR-AUTH-003`، `PRD-SEC-001`).

## ۷. عملیات تراکنشی

| اصل | توضیح |
|---|---|
| تراکنش در هر درخواست نوشتن | هر درخواست نوشتن، یک واحد کار منطقی است |
| بدون موفقیت جزئی | تأیید سفارش با چند قلم، یا همه اقلام رزرو می‌شوند یا هیچ‌کدام |
| مرز ماژول | عملیات چندماژولی در لایه کاربرد هماهنگ می‌شود (`ARCH-P-005`) |
| ممیزی در تراکنش | برای عملیات حساس، ثبت ممیزی بخشی از همان تراکنش است |
| اثر جانبی بیرونی | ارسال پیامک/ایمیل یا فایل، خارج از تراکنش دامنه و با جبران صریح (در صورت ورود به محدوده) |
| پاسخ پس از ثبت | پاسخ موفق فقط پس از تأیید تراکنش بازگردانده می‌شود |
| خطای وسط کار | بازگشت کامل؛ هیچ رزرو یا گردش نیمه‌کاره باقی نمی‌ماند |

## ۸. جلوگیری از درخواست تکراری (Idempotency)

**عملیات الزام‌شده:** ایجاد سفارش، تأیید سفارش، لغو سفارش، رزرو/آزادسازی، ثبت ارسال، ثبت تحویل، ثبت مرجوعی، اصلاح موجودی.

| قاعده | توضیح |
|---|---|
| هدر | `Idempotency-Key` با مقدار یکتای تولیدشده توسط کلاینت |
| دامنه یکتایی | (شرکت، نوع عملیات، کلید) |
| نخستین درخواست | پردازش، ذخیره نتیجه و بازگرداندن پاسخ اصلی |
| درخواست تکراری با همان بدنه | بازگرداندن همان پاسخ با نشانه `Idempotent-Replay: true` |
| درخواست تکراری با بدنه متفاوت | خطای `IDEMPOTENCY_KEY_REUSED` بدون اثر جانبی |
| درخواست هم‌زمان با همان کلید | یکی پردازش می‌شود؛ دیگری منتظر یا با تعارض مشخص پاسخ می‌گیرد |
| نبود هدر در عملیات الزام‌شده | خطای `VALIDATION_ERROR` (پیشنهاد سخت‌گیرانه) |
| مدت نگهداشت رکورد | **نیازمند تصمیم** در `PH-5`؛ در این سند عدد تعیین نمی‌شود |
| داده ذخیره‌شده | خلاصه پاسخ، نه داده حساس کامل |

**پیشنهاد تولید کلید در کلاینت:** یک کلید به‌ازای هر «تلاش برای ثبت یک سند» تولید شود و تا دریافت نتیجه قطعی یا انصراف کاربر حفظ شود؛ پس از ثبت موفق، کلید جدید برای سند بعدی. این رفتار برای پوشش `BR-OFF-003` ضروری است.

## ۹. هم‌زمانی درخواست‌ها

| سناریو | رفتار پیشنهادی |
|---|---|
| ویرایش هم‌زمان یک رکورد | استفاده از `version` یا `ETag`؛ در صورت تعارض `STALE_VERSION` |
| دو تأیید هم‌زمان یک سفارش | یکی موفق؛ دیگری `STATE_CONFLICT` بدون اثر جانبی |
| رزرو هم‌زمان موجودی ناکافی | یکی موفق؛ دیگری `STOCK_INSUFFICIENT` |
| آزادسازی دوباره رزرو | بی‌اثر یا `STATE_CONFLICT`؛ موجودی افزایش نمی‌یابد |
| ارسال هم‌زمان دو تحویل | مجموع تحویل از ارسال بیشتر نمی‌شود |
| اصلاح موجودی هم‌زمان | اعمال ترتیبی با کنترل نسخه؛ بدون گم‌شدن تغییر |

**قاعده:** کنترل هم‌زمانی در سرور و پایگاه داده انجام می‌شود؛ کلاینت فقط می‌تواند تعارض را نمایش دهد و امکان بازخوانی و تلاش مجدد بدهد. قفل طولانی یا قفل سمت کلاینت مبنای طراحی نیست.

## ۱۰. تاریخ، زمان، واحد پول و مقادیر اعشاری

### ۱۰.۱. زمان

| موضوع | قرارداد |
|---|---|
| ذخیره‌سازی | زمان استاندارد یکنواخت (UTC) با دقت مشخص |
| منطقه زمانی کسب‌وکار | `Asia/Tehran` برای تفسیر و نمایش |
| قالب انتقال | ISO 8601 با نشانه منطقه زمانی |
| نمایش در رابط کاربری | تقویم شمسی و ساعت محلی تهران |
| فیلد تاریخ کاری | در صورت نیاز به تاریخ بدون زمان، قالب `YYYY-MM-DD` با معنای تاریخ محلی |
| مرز روز در گزارش | بر اساس `Asia/Tehran`، نه UTC |
| مهلت‌ها | اختلاف زمان با زمان استاندارد، نه با ساعت دستگاه |

### ۱۰.۲. مبالغ و واحد پول

| موضوع | قرارداد پیشنهادی | وضعیت |
|---|---|---|
| واحد پول | از تنظیمات شرکت؛ هرگز مقدار ثابت در مسیر یا کد | `DEC-002` |
| انتقال مبلغ | **رشته اعشاری** (مثل `"125000.00"`) برای جلوگیری از خطای ممیز شناور | پیشنهادی |
| ذخیره‌سازی | نوع عددی دقیق پایگاه داده با مقیاس مشخص | پیشنهادی |
| دقت و گردکردن | مطابق `OD-CAT-001-A` و `OD-CAT-001-B` | **نیازمند تصمیم** |
| مقدار کالا | عدد صحیح در نسخه اولیه (پیشنهاد) | **نیازمند تصمیم** `OD-CAT-001-A` |
| نمایش | قالب‌بندی فارسی، جداکننده هزارگان، واحد پول شرکت | پیشنهادی |
| محاسبه | در سرور؛ کلاینت فقط نمایش | الزامی |

نمونه (ساختگی و فقط توضیحی؛ واحد پول نمونه است و مقدار واقعی از تنظیمات شرکت می‌آید):

```json
{
  "data": {
    "id": "st_example_001",
    "currency": "IRR",
    "items": [
      {
        "productId": "prd_example_001",
        "quantity": 3,
        "unitPrice": "125000.00",
        "lineTotal": "375000.00"
      }
    ],
    "total": "375000.00"
  },
  "meta": { "requestId": "req_example_004" }
}
```

> اگر در آینده واحد پول با دقت اعشاری متفاوت پشتیبانی شود، مقیاس هر واحد پول باید صریح باشد و در قرارداد پاسخ اعلام شود.

## ۱۱. ثبت رخداد و اطلاعات عیب‌یابی

| موضوع | قاعده |
|---|---|
| شناسه درخواست | تولید در سرور یا پذیرش `X-Request-Id` معتبر؛ برگشت در پاسخ و هدر |
| همبستگی | همان شناسه در لاگ‌های سرویس و پایگاه داده قابل پیگیری باشد |
| لاگ درخواست | متد، مسیر، کد وضعیت، زمان پردازش، شناسه کاربر و شرکت (بدون داده شخصی اضافه) |
| بدنه درخواست | **ثبت نمی‌شود** در حالت عادی؛ در صورت نیاز، فقط با پوشاندن داده حساس |
| خطا | کد پایدار، شناسه پیگیری و محل خطا در لاگ داخلی ثبت می‌شود |
| ممیزی | جدا از لاگ فنی؛ رویدادهای دامنه‌ای در پایگاه داده (`ENT-AUDIT-EVENT`) |
| پاسخ به کاربر | فقط `requestId` و پیام قابل‌فهم؛ بدون جزئیات داخلی |
| داده حساس در لاگ | رمز، توکن، کد یک‌بارمصرف، شماره کامل تماس و موقعیت دقیق در لاگ ثبت نمی‌شود |
| پایش | نرخ خطا، نرخ رد مجوز، تعارض موجودی و تأخیر endpointهای اصلی |

| موضوع | گزینه‌ها | اثر | مرجع |

| روش انتقال شرکت فعال | هدر `X-Company-Id`؛ یا مسیر `/companies/{id}` | تغییر شکننده در همه کلاینت‌ها | این سند، بخش ۴.۱ |

| به‌روزرسانی زنده وضعیت | بدون push در نسخه اولیه؛ بازآوری دوره‌ای | پیچیدگی زیرساخت | `ARCH-P-010` |
