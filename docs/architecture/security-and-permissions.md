## ۲. جداسازی داده شرکت‌ها در همه لایه‌ها

اصل: جداسازی شرکت یک الزام در همه لایه‌ها است، نه یک فیلتر در رابط کاربری.

| لایه | الزام |
|---|---|
| رابط کاربری | فقط داده شرکت فعال نمایش داده می‌شود؛ تغییر شرکت فعال، زمینه همه درخواست‌ها را تغییر می‌دهد. |
| احراز هویت | نشست، عضویت‌های کاربر را مشخص می‌کند؛ شرکت فعال از میان آن‌ها انتخاب می‌شود. |
| API | هر درخواست دامنه شرکت باید زمینه شرکت معتبر داشته باشد؛ نبود آن رد می‌شود. |
| لایه کاربرد | زمینه شرکت به‌صورت شیء صریح و تغییرناپذیر در طول عملیات منتقل می‌شود؛ نه از پارامترهای اختیاری. |
| دسترسی داده | هر کوئری دامنه شرکت باید فیلتر شرکت داشته باشد؛ کوئری بدون فیلتر ممنوع. |
| پایگاه داده | ستون مالکیت اجباری، مراجع مرکب شرکت‌محور، محدودیت‌های یکتایی شرکت‌محور، RLS **اجباری** به‌عنوان لایه دوم (`DEC-006`). |
| کارهای پس‌زمینه | هر کار باید زمینه شرکت صریح داشته باشد؛ کار بدون زمینه ممنوع. |
| گزارش‌ها | همه گزارش‌ها محدود به شرکت فعال و مجوز کاربر؛ پارامترهای گزارش نمی‌توانند مرز شرکت را جابه‌جا کنند. |
| کش | کلید کش شامل شرکت است؛ داده حساس شرکت کش نمی‌شود. |
| لاگ و ممیزی | رویداد شرکت A هرگز در دسترس کاربر شرکت B قرار نمی‌گیرد. |
| پشتیبان‌گیری | پشتیبان شامل داده همه شرکت‌ها است و دسترسی به آن بسیار محدود و ممیزی‌شده است. |
| خروجی فایل | خروجی محدود به همان شرکت و همان درخواست است؛ فایل با دسترسی عمومی ذخیره نمی‌شود. |

**قواعد الزامی:**

- `BR-TEN-001` تا `BR-TEN-003` مبنای طراحی هستند.
- هر endpoint جدید باید آزمون «دسترسی افقی» داشته باشد.
- هیچ مسیر «پشتیبانی» یا «دیباگ» نباید مرز شرکت را دور بزند، مگر با تصمیم صریح و طراحی ممیزی‌شده.

**تصمیم اجرایی (`DEC-006`):** ستون مالکیت شرکت در همه جدول‌های عملیاتی + کنترل دسترسی برنامه + Row-Level Security به‌عنوان لایه دفاعی دوم. جزئیات پیاده‌سازی فاز ۱ در [phase-1.md](../implementation/phase-1.md).

## ۳. کنترل دسترسی مبتنی بر نقش و شرکت

### ۳.۱. مدل پیشنهادی

```text
User ──< CompanyMembership >── Company
                 │
                 └── Role ──< RolePermission >── Permission
```

- مجوز از عضویت همان شرکت گرفته می‌شود (`BR-AUTH-002`).
- شرکت فعال صرفاً انتخاب زمینه است؛ مرجع مجوز نیست.
- بررسی مجوز در یک لایه مرکزی انجام می‌شود و نتیجه آن قابل آزمون است.
- محدودیت‌های سطح رکورد (مثلاً فروشگاه‌های مجاز) جدا از مجوز نوع عملیات اعمال می‌شوند.

### ۳.۲. اصول بررسی مجوز

| شناسه | اصل |
|---|---|
| `AUTHZ-01` | هیچ endpointی بدون بررسی صریح مجوز اجرا نمی‌شود؛ پیش‌فرض «رد». |
| `AUTHZ-02` | بررسی مجوز پیش از اجرای منطق دامنه و پیش از هر بازخوانی داده انجام می‌شود. |
| `AUTHZ-03` | شناسه شرکت و مالکیت رکورد در سرور بررسی می‌شود؛ نه در کلاینت. |
| `AUTHZ-04` | عملیات سطح پلتفرم از مسیر و مجوز جداگانه استفاده می‌کند. |
| `AUTHZ-05` | تغییر نقش و عضویت خود کاربر توسط خودش مجاز نیست. |
| `AUTHZ-06` | رد دسترسی، پاسخ یکسان و بدون افشای وجود رکورد دارد. |
| `AUTHZ-07` | افزودن مجوز جدید نیازمند ثبت در کاتالوگ، مستندسازی و آزمون است. |
| `AUTHZ-08` | دسترسی پیش‌فرض هیچ نقشی به داده شرکت دیگر وجود ندارد. |

## ۴. عدم اعتماد به داده شرکت از سمت کلاینت

| ورودی | خطر | رفتار الزامی |
|---|---|---|
| `X-Company-Id` یا پارامتر شرکت | جعل شرکت | بررسی عضویت فعال کاربر در آن شرکت |
| `companyId` در بدنه | جعل مالکیت رکورد | نادیده گرفتن یا رد؛ مالکیت از زمینه معتبر سرور |
| `userId` در بدنه | جعل هویت عامل | استفاده از هویت نشست |
| `storeId`/`productId`/`orderId` | ارجاع به شرکت دیگر | بررسی تعلق به شرکت جاری در همان پرس‌وجو |
| نقش یا مجوز در بدنه | ارتقای دسترسی | نادیده گرفتن کامل؛ نقش فقط از عضویت |
| وضعیت یا تأییدکننده | جعل تأیید | تعیین در سرور بر اساس عملیات مجاز |
| مبلغ/قیمت ارسالی | دستکاری مالی | محاسبه قیمت از کاتالوگ یا اعتبارسنجی صریح مجاز |

**الزام:** در صورت رد داده نامعتبر، خطا باید بدون افشای وجود یا نبود رکورد در شرکت دیگر باشد.

## ۵. جداسازی هویت و نشست مدیر پلتفرم

| الزام | توضیح |
|---|---|
| هویت مستقل | `ENT-PLATFORM-ADMIN` جدا از `ENT-USER`؛ امکان استفاده متقابل وجود ندارد. |
| مسیر ورود مستقل | ورود مدیر پلتفرم از مسیر جداگانه و با سیاست احراز هویت قوی‌تر. |
| نشست مستقل | نشست مدیر پلتفرم قابل استفاده برای مسیرهای شرکت نیست و برعکس. |
| بدون زمینه شرکت | مسیرهای پلتفرم هدر شرکت را نمی‌پذیرند یا نادیده می‌گیرند. |
| دسترسی پیش‌فرض حداقلی | مدیر پلتفرم به‌صورت پیش‌فرض به داده عملیاتی شرکت‌ها دسترسی ندارد. |
| دسترسی پشتیبانی | پیش‌فرض «بدون دسترسی»؛ در صورت نیاز، دسترسی موقت، مستند، تأییدشده و کاملاً ممیزی‌شده؛ **نیازمند تصمیم `OD-PERM-003`** |
| احراز هویت قوی | ورود دومرحله‌ای برای مدیر پلتفرم پیشنهاد می‌شود؛ وابسته به `OD-AUTH-002` |
| ممیزی | همه عملیات سطح پلتفرم و همه دسترسی‌های پشتیبانی ثبت می‌شوند. |

## ۶. حفاظت از اعتبارنامه، نشست و توکن

| موضوع | قاعده پیشنهادی |
|---|---|
| ذخیره رمز | فقط هش با الگوریتم کند و حافظه‌بر (مثل Argon2id) با نمک یکتا؛ Text ساده یا هش سریع ممنوع |
| سیاست رمز | حداقل طول و رد رمزهای رایج؛ جزئیات عددی در `OD-AUTH-002` |
| نمایش رمز | هرگز در پاسخ، لاگ یا خطا؛ ورود رمز در فرم با ماسک |
| بازیابی حساب | توکن یک‌بارمصرف و کوتاه‌عمر؛ بی‌اثر شدن پس از استفاده؛ عدم افشای وجود حساب |
| کوکی | `HttpOnly`، `Secure`، `SameSite` مناسب، دامنه محدود، بدون داده حساس در کوکی |
| توکن | کوتاه‌عمر، قابل ابطال، بدون داده حساس در payload، ذخیره امن در کلاینت |
| چرخش | چرخش شناسه نشست پس از ورود و تغییر سطح دسترسی |
| ابطال | خروج، تغییر رمز، غیرفعال‌سازی کاربر و تغییر نقش باید نشست‌های مربوط را باطل یا مجدداً ارزیابی کند |
| نشست‌های هم‌زمان | سیاست تعداد و رفتار ابطال وابسته به `OD-AUTH-002` |
| اسرار سامانه | خارج از مخزن، قابل چرخش، بدون درج در لاگ و مستندات |
| دسترسی پایگاه داده | حداقل امتیاز؛ تفکیک کاربر اجرا از کاربر مهاجرت (پیشنهاد) |

**نکته:** روش احراز هویت با `DEC-005` (موبایل + رمز عبور) و جزئیات نشست با `IMP-001`/`OD-AUTH-003` تثبیت شده است. اصول حفاظتی این بخش در فاز ۱ پیاده‌سازی شده‌اند.

## ۷. ابطال نشست و مدیریت کاربر غیرفعال

| رخداد | رفتار الزامی |
|---|---|
| غیرفعال‌سازی کاربر | رد درخواست‌های بعدی و ابطال نشست‌های فعال |
| غیرفعال‌سازی عضویت در یک شرکت | از دست رفتن دسترسی به همان شرکت، بدون اثر بر شرکت‌های دیگر |
| حذف/تغییر نقش | ارزیابی مجدد مجوز در درخواست بعدی؛ ابطال نشست جاری توصیه می‌شود |
| تغییر رمز | ابطال سایر نشست‌ها (پیشنهاد) |
| خروج | ابطال نشست جاری |
| تعلیق شرکت | محدودسازی عملیات مطابق `OD-STORE-003`؛ داده حذف نمی‌شود |
| انقضای نشست | نیازمند ورود مجدد؛ وابسته به `OD-AUTH-002` |

**الزام:** ابطال نباید فقط به عمر نشست متکی باشد؛ بررسی وضعیت کاربر و عضویت بخشی از هر درخواست است (`BR-AUTH-004`).

## ۸. ثبت رویدادهای ممیزی

| رویداد | حداقل اطلاعات | فاز |
|---|---|---|
| ورود موفق و ناموفق | هویت، زمان، نشانی شبکه، نتیجه | `PH-1` |
| غیرفعال‌سازی/فعال‌سازی کاربر | عامل، هدف، زمان | `PH-1` |

| ایجاد/تغییر/تعلیق مجوز | عامل پلتفرم، مقدار قبلی/جدید | `PH-8` (پایه در `PH-1`) |
| ایجاد/ویرایش/غیرفعال‌سازی فروشگاه | عامل، فروشگاه، تغییرات مهم | `PH-2` |
| تغییر موقعیت مکانی فروشگاه | مقدار قبلی/جدید و منبع | `PH-2` |
| ایجاد/تغییر قیمت | محصول، مقدار قبلی/جدید | `PH-3` |
| ثبت موجودی اولیه و اصلاح موجودی | محصول، مقدار، دلیل، مجوز | `PH-4` |
| رزرو، آزادسازی و مصرف رزرو | محصول، مقدار، سند مرجع | `PH-4` |

| تغییر قیمت قلم پس از ثبت (در صورت مجاز بودن) | مقدار قبلی/جدید، مجوز | `PH-5` |
| ارسال، تحویل و مرجوعی | سند، مقدار، عامل | `PH-6` |
| دسترسی به داده مکانی | کاربر، فروشگاه، هدف دسترسی | `PH-2` |
| رد دسترسی حساس (نمونه‌گیری‌شده) | کاربر، منبع، دلیل | `PH-1` |

**قواعد:**

- رویداد ممیزی فقط‌افزودنی است و مسیر ویرایش/حذف ندارد (`BR-AUD-002`).
- برای عملیات مالی و انباری حساس، ثبت ممیزی بخشی از تراکنش اصلی است.
- داده حساس (رمز، توکن، شماره کامل تماس، موقعیت دقیق) در بدنه رویداد ثبت نمی‌شود؛ در صورت نیاز فقط ارجاع به رکورد.
- دسترسی به ممیزی شرکت فقط برای نقش صریحاً مجاز؛ دسترسی سطح پلتفرم جدا.
- ثبت تلاش‌های ناموفق دسترسی باید محدود و نمونه‌گیری شود تا خودش ابزار سوءاستفاده یا پرکننده دیسک نباشد.

## ۱۰. جلوگیری از دسترسی غیرمجاز بین شرکت‌ها

### ۱۰.۱. کنترل‌های پیشنهادی

| لایه | کنترل |
|---|---|
| مسیر و API | زمینه شرکت اجباری و اعتبارسنجی‌شده |
| برنامه | مجوزدهی مرکزی + محدودیت سطح رکورد |
| پرس‌وجو | فیلتر شرکت در همه کوئری‌های دامنه شرکت |
| پایگاه داده | مراجع شرکت‌محور، یکتایی شرکت‌محور، RLS اجباری با دو نقش جدا (`DEC-006`) |
| آزمون | سناریوهای دسترسی افقی برای هر منبع و هر نقش |
| بازبینی | بازبینی کد برای هر کوئری جدید دامنه شرکت |
| ممیزی | ثبت دسترسی‌های حساس و ردهای مشکوک |

### ۱۰.۲. Row-Level Security — دفاع چندلایه

اگر RLS انتخاب شود (`OD-DATA-001`):

- **جایگزین کنترل دسترسی برنامه نیست.** خطای طراحی یا نادیده گرفتن سیاست در برنامه نباید تنها با RLS جبران شود.
- سیاست‌ها باید شرکت جاری نشست پایگاه داده را با مالکیت رکورد مقایسه کنند.
- مسیر اتصال pooling و تنظیم متغیر نشست باید کنترل‌شده باشد تا زمینه شرکت بین درخواست‌ها نشت نکند.
- کاربر پایگاه داده اجرای برنامه نباید مالک جدول‌ها باشد و نباید بتواند سیاست‌ها را تغییر دهد (پیشنهاد).
- برای مسیرهای سطح پلتفرم و گزارش‌های پلتفرم، سیاست جداگانه و صریح لازم است؛ نه غیرفعال کردن عمومی RLS.
- مهاجرت‌ها و عملیات نگهداشت باید با کاربر پایگاه داده جداگانه انجام شوند.
- آزمون‌ها باید هم با RLS و هم با بررسی برنامه اجرا شوند تا معلوم شود کدام لایه از دسترسی جلوگیری کرده است.
