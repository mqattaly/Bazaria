# بازاریا (Bazaria)

> **وضعیت پروژه: فاز ۲ در محدوده مصوب پیاده‌سازی شده — در انتظار تأیید برای فاز ۳.**
> فاز ۰ (مستندسازی)، فاز ۱ (زیرساخت، هویت، عضویت چندشرکتی، جداسازی داده و RLS) و فاز ۲ (چرخه اشتراک، مهلت ارفاقی، فقط‌خواندنی، تمدید و مدیریت پایه فروشگاه) انجام شده‌اند. GPS، تشخیص تکراری و دامنه فروش طبق `DEC-011` به فازهای بعد موکول شده‌اند.
>
> **هشدار:** تصمیم‌های قطعی کاربر با برچسب `CONFIRMED_BY_USER` مشخص شده‌اند. پیش‌فرض‌های اجرایی فازها با شناسه `IMP-*` و وضعیت `IMPLEMENTED_DEFAULT` ثبت شده‌اند و تصمیم قطعی کاربر نیستند؛ سایر موارد یا تصمیم باز (`OPEN`) هستند یا پیشنهاد نیازمند تأیید (`PROPOSAL` / `PROVISIONAL`).

---

## ۱. بازاریا چیست؟

بازاریا یک سامانه چندشرکتی (Multi-Company) برای مدیریت عملیات فروش و توزیع محصولات است. تمرکز نسخه اولیه بر ثبت سریع مشتریان فروشگاهی، مدیریت کاتالوگ و قیمت، کنترل موجودی، ثبت و تأیید سفارش، آماده‌سازی و تحویل سفارش و گزارش‌گیری است.

سامانه برای استفاده روزمره نیروهای فروش و کارکنان انبار طراحی می‌شود: ساده، سریع، قابل‌اعتماد و مناسب موبایل، با رابط کاربری فارسی و راست‌چین.

## ۲. مسئله‌ای که محصول حل می‌کند

در کسب‌وکارهای توزیع و پخش، اطلاعات فروشگاه‌ها، قیمت‌ها، موجودی و سفارش‌ها معمولاً بین چند ابزار پراکنده است (دفتر، فایل‌های صفحه‌گسترده، پیام‌رسان و حافظه افراد). این پراکندگی به این مشکلات منجر می‌شود:

- تکرار ثبت فروشگاه‌ها و نبود تصویر واحد از مشتریان فروشگاهی.
- نامشخص بودن موجودی قابل‌استفاده در لحظه ثبت سفارش و در نتیجه فروش بیش از موجودی.
- کندی و خطای انسانی در ثبت سفارش روی موبایل، به‌ویژه در شرایط اتصال ضعیف اینترنت.
- نبود ردپای قابل حسابرسی از تأیید سفارش، تغییر قیمت و اصلاح موجودی.
- نبود گزارش قابل‌اتکا از فروش، سفارش، موجودی و عملکرد کاربران.
- دشواری جداسازی داده چند کسب‌وکار یا چند شرکت زیر یک سامانه مشترک.

بازاریا این فرایندها را در یک سامانه واحد با جداسازی داده شرکت‌ها، گردش موجودی قابل ممیزی و رابط کاربری سریع یکپارچه می‌کند.

## ۳. کاربران و نقش‌های اصلی

| نقش | زمینه | مسئولیت کلی |
|---|---|---|
| **Platform Admin** | سطح پلتفرم (خارج از شرکت) | مدیریت سطح پلتفرم، ایجاد شرکت‌ها، مدیریت تنظیمات و مجوز استفاده از سامانه |
| **Manager** | داخل یک شرکت | مدیریت کاربران شرکت، کاتالوگ، عملیات فروش، تأیید سفارش و گزارش‌ها بر اساس مجوزهای نهایی |
| **Sales Representative** | داخل یک شرکت | مشاهده اطلاعات مجاز، ثبت و پیگیری فروشگاه‌ها و ایجاد سفارش در محدوده دسترسی خود |
| **Warehouse User** | داخل یک شرکت | مشاهده موجودی مجاز، آماده‌سازی سفارش‌ها و ثبت عملیات انبار و ارسال بر اساس مجوزها |

نقش‌ها **نقطه شروع تحلیل** هستند؛ مجموعه مجوز دقیق هر نقش تا زمان تصمیم‌گیری نهایی، در [ماتریس دسترسی](docs/architecture/security-and-permissions.md) با وضعیت «نیازمند تصمیم» مشخص شده است.

اصول کلیدی نقش‌ها:

- یک کاربر عملیاتی می‌تواند عضو چند شرکت باشد و نقش او در هر شرکت مستقل تعریف می‌شود (`DEC-001`).
- **Platform Admin** هویتی جدا از کاربران شرکت‌ها دارد و نشست او نباید با نشست کاربر عادی اشتباه شود.
- هیچ کاربری به‌صورت پیش‌فرض به داده شرکت دیگر دسترسی ندارد.

## ۴. قابلیت‌های اصلی نسخه اولیه

- **هویت و عضویت:** ورود کاربر، عضویت چندشرکتی، انتخاب شرکت فعال، نقش مستقل در هر شرکت، مدیریت کاربران شرکت.
- **شرکت و مجوز استفاده:** ایجاد شرکت توسط مدیر پلتفرم، اطلاعات پایه شرکت، واحد پول مستقل هر شرکت، اطلاعات پایه مجوز استفاده (از جمله سقف تعداد فروشگاه).
- **فروشگاه‌ها (پیاده‌سازی‌شده در `PH-2`):** ثبت، ویرایش، فعال/غیرفعال، اطلاعات تماس و آدرس، جست‌وجو، فیلتر و صفحه‌بندی؛ GPS و تشخیص تکراری به فاز بعد موکول شده‌اند (`DEC-011`).
- **اشتراک شرکت (پیاده‌سازی‌شده در `PH-2`):** چرخه اعتبار و مهلت ارفاقی، مسدودسازی نوشتن در حالت فقط‌خواندنی و تمدید از مسیر مدیر پلتفرم (`DEC-010`).
- **کاتالوگ و قیمت:** محصولات، کد کالا، وضعیت فعال/غیرفعال، قیمت هر شرکت، واحد پول شرکت.
- **انبار:** موجودی اولیه، گردش موجودی قابل ممیزی، اصلاح موجودی، رزرو و آزادسازی رزرو، جلوگیری از موجودی منفی.
- **سفارش‌ها:** ثبت سریع سفارش روی موبایل، پیش‌نویس محلی، اعتبارسنجی، تأیید مدیر، تاریخچه وضعیت، جلوگیری از سفارش تکراری.
- **آماده‌سازی و توزیع:** آماده‌سازی، ارسال و ثبت خروج فیزیکی کالا، تحویل کامل یا جزئی، مرجوعی مطابق تصمیم‌های نهایی.
- **گزارش‌ها:** گزارش فروش، سفارش، موجودی و عملکرد کاربران با رعایت جداسازی داده شرکت‌ها.

## ۵. اصول محصول

1. **فارسی و راست‌چین (RTL):** زبان اصلی رابط کاربری فارسی است و تمام صفحات عملیاتی راست‌چین طراحی می‌شوند.
2. **سرعت:** عملیات پرتکرار (ثبت سفارش، افزودن کالا، مشاهده موجودی) با کمترین تعداد مرحله و کلیک انجام می‌شود.
3. **سادگی:** رابط کاربری خلوت و قابل‌فهم برای نیروی فروش و انبار، با خطاهای روشن و قابل‌اقدام.
4. **صحت عملیات انبار و سفارش:** تغییرات موجودی فقط از مسیرهای قابل ممیزی انجام می‌شود و موجودی منفی ممکن نیست.
5. **امنیت و جداسازی شرکت‌ها:** هر درخواست در سمت سرور از نظر عضویت، شرکت فعال و مجوز بررسی می‌شود؛ به شناسه شرکت ارسالی از سمت کاربر اعتماد نمی‌شود.
6. **قابلیت اتکا در اتصال ضعیف:** فرم‌های در حال تکمیل به‌صورت پیش‌نویس محلی ذخیره می‌شوند و ارسال ناموفق قابل تلاش مجدد است؛ بدون آنکه ارسال دوباره به سفارش تکراری منجر شود.
7. **توسعه فازبه‌فاز:** هر فاز محدوده، معیار پذیرش و قراردادهای مستقل دارد و تغییر قراردادهای تثبیت‌شده بدون بررسی اثر مجاز نیست.

## ۶. تصمیم‌های قطعی ثبت‌شده

| شناسه | موضوع | وضعیت |
|---|---|---|
| `DEC-001` | عضویت چندشرکتی با نقش مستقل در هر شرکت و امکان انتخاب شرکت فعال | `CONFIRMED_BY_USER` |
| `DEC-002` | واحد پول در سطح هر شرکت قابل‌تنظیم است و سراسری فرض نمی‌شود | `CONFIRMED_BY_USER` |
| `DEC-003` | ذخیره پیش‌نویس محلی فرم و تلاش مجدد ارسال در نسخه اولیه؛ Offline کامل خارج از محدوده | `CONFIRMED_BY_USER` |
| `DEC-004` | ماژول انبار پیش از ماژول سفارش‌ها پیاده‌سازی می‌شود | `CONFIRMED_BY_USER` |
| `DEC-005` | ورود کاربران شرکت با شماره موبایل و رمز عبور؛ بازیابی حساب با کد یک‌بارمصرف | `CONFIRMED_BY_USER` |
| `DEC-006` | پایگاه داده مشترک + کنترل دسترسی در برنامه + Row-Level Security به‌عنوان لایه دوم | `CONFIRMED_BY_USER` |
| `DEC-007` | پشته فناوری: React + TypeScript + Tailwind، NestJS + TypeScript، PostgreSQL | `CONFIRMED_BY_USER` |
| `DEC-008` | اختیارات مدیریتی متناسب با نقش و ممیزی عملیات حساس | `CONFIRMED_BY_USER` |
| `DEC-009` | هویت و مسیر احراز هویت مستقل مدیر پلتفرم با راه‌اندازی کنترل‌شده | `CONFIRMED_BY_USER` |

جزئیات و نگاشت این تصمیم‌ها به شناسه‌های مرجع (`OD-*`) در [سند تصمیم‌های باز](docs/product/open-decisions.md) آمده است. این تصمیم‌ها دوباره به‌عنوان سؤال باز مطرح نمی‌شوند؛ فقط جزئیات اجرایی حل‌نشده به‌صورت زیرسؤال مستقل ثبت شده‌اند.

### نشانه‌گذاری وضعیت در مستندات

| برچسب | معنا |
|---|---|
| `CONFIRMED_BY_USER` | تصمیم قطعی اعلام‌شده توسط کاربر؛ مبنای طراحی است |
| `OPEN` | تصمیم حل‌نشده؛ گزینه‌ها و پیشنهاد ثبت شده و تصمیم با کاربر است |
| `PROPOSAL` | پیشنهاد معماری یا محصول؛ تا تأیید، قطعی نیست |
| `PROVISIONAL` | قاعده موقت که به یک تصمیم باز وابسته است |
| `OUT_OF_SCOPE` | صراحتاً خارج از محدوده نسخه اولیه |
| `DEFERRED` | به فاز بعد موکول شده است |
| `PARTIALLY_RESOLVED` | بخشی از یک پرسش باز با تصمیم قطعی پاسخ داده شده و بقیه به شناسه باز جدید منتقل شده است |
| `IMPLEMENTED_DEFAULT` | پیش‌فرض اجرایی پیاده‌سازی‌شده در یک فاز؛ تصمیم قطعی کاربر نیست |

### شناسه‌ها

- `DEC-*` — تصمیم قطعی کاربر.
- `OD-*` — تصمیم باز یا قطعی ثبت‌شده در سند تصمیم‌های باز.
- `PRD-*` — نیازمندی محصول (مثال: `PRD-ORD-001`).
- `BR-*` — قاعده کسب‌وکار (مثال: `BR-INV-001`).
- `FLOW-*` — جریان کسب‌وکار.
- `AC-*` — معیار پذیرش قابل‌آزمایی.
- `MOD-*` — ماژول معماری.
- `ENT-*` — موجودیت مفهومی داده.
- `PH-*` — فاز توسعه.
- `ARCH-P-*` — پیشنهاد معماری نیازمند تأیید.
- `CON-*` — قرارداد مشترک بین فازها (مرجع: [نقشه راه](docs/architecture/phase-roadmap.md)).
- `IMP-*` — تصمیم اجرایی فاز (پیش‌فرض پیاده‌سازی‌شده، ارجاع‌دهنده به `DEC-*`).

## ۸. نقشه راه فازها

| فاز | عنوان | خروجی اصلی |
|---|---|---|
| `PH-0` | مستندات و تصمیم‌های محصول | انجام‌شده — مستندات فاز ۰ |
| `PH-1` | زیرساخت و هویت | انجام‌شده — ساختار پروژه، پایگاه داده، احراز هویت، شرکت‌ها، عضویت، نقش‌ها، RLS و رابط پایه |
| `PH-2` | فروشگاه‌ها | ثبت/ویرایش/جست‌وجو، GPS، تشخیص تکراری، سقف فروشگاه، UI فارسی و RTL |
| `PH-3` | کاتالوگ و قیمت | محصولات، قیمت شرکت، واحد پول شرکت، اعتبارسنجی مقادیر |
| `PH-4` | انبار | موجودی اولیه، گردش‌های قابل‌ممیزی، اصلاح، رزرو/آزادسازی، جلوگیری از موجودی منفی |
| `PH-5` | سفارش‌ها | ثبت سریع، پیش‌نویس، تأیید مدیر، تراکنش سازگار با انبار، جلوگیری از سفارش تکراری |
| `PH-6` | آماده‌سازی و توزیع | آماده‌سازی، ارسال، تحویل کامل/جزئی، مرجوعی |
| `PH-7` | گزارش‌ها | گزارش فروش، سفارش، موجودی و عملکرد کاربران |
| `PH-8` | مدیریت کامل پلتفرم و مجوزها | مدیریت شرکت‌ها، سقف‌ها، وضعیت مجوز و گزارش‌های سطح پلتفرم |

وابستگی اصلی: `PH-0 → PH-1 → PH-2 → PH-3 → PH-4 → PH-5 → PH-6 → PH-7`. فاز `PH-8` به زیرساخت و اطلاعات پایه `PH-1` و نیازهای سایر فازها وابسته است، اما نباید مرزهای امنیتی و مالکیت داده را دور بزند.

جزئیات، پیش‌نیازها، موارد خارج از محدوده و معیارهای پذیرش هر فاز در [نقشه راه](docs/architecture/phase-roadmap.md) آمده است.

## ۹. وضعیت فعلی پروژه

- **فازهای انجام‌شده:** `PH-0` (مستندسازی)، `PH-1` (زیرساخت، هویت و جداسازی داده شرکت‌ها) و `PH-2` در محدوده `DEC-010`/`DEC-011` (اشتراک و فروشگاه پایه).
- **کد اجرایی:** monorepo با `apps/api` (NestJS)، `apps/web` (React + Tailwind) و `packages/shared`.
- **پایگاه داده:** migrationهای نسخه‌دار `001_phase1_foundation.sql` و `002_phase2_stores.sql`، دو نقش جدا (`bazaria_owner` و `bazaria_app`) و RLS فعال و `FORCE` روی جدول‌های شرکت‌محور.
- **آزمون‌ها:** ۱۰۴ آزمون API (واحد، یکپارچگی، امنیتی و RLS با نقش واقعی) و ۳۱ آزمون رابط کاربری، اجراشده و سبز.
- **تصمیم‌های باز:** `OD-PERM-001`، `OD-STORE-001`، `OD-STORE-003` (گردش‌کار افزایش سقف)، `OD-AUTH-003`، `OD-MEM-001` و سایر موارد در [open-decisions.md](docs/product/open-decisions.md). `OD-LIC-002` با `DEC-010` حل شد.
- **گام بعدی:** تأیید صریح کاربر برای شروع `PH-3`. پایان فاز ۲ به‌معنای تأیید خودکار فاز بعدی نیست.

### اجرای محلی (خلاصه)

```bash
npm install
cp .env.example .env                 # جای‌نگهدارهای YOUR_* را با رمز محلی جایگزین کنید
npm run db:start                     # PostgreSQL 18 محلی از بسته npm (پنجره جدا)
npm run db:bootstrap                 # ساخت نقش‌ها و پایگاه داده
npm run db:migrate                   # اجرای migrationها
npm run db:seed:dev                  # داده نمونه توسعه؛ رمز یک‌بار چاپ می‌شود
npm run platform-admin:create -- --username admin --name "مدیر پلتفرم"
npm run dev                          # API روی 3000 و وب روی 5173
```

راهنمای کامل و محدودیت‌های هر فاز در [docs/implementation/phase-1.md](docs/implementation/phase-1.md) و [docs/implementation/phase-2.md](docs/implementation/phase-2.md) آمده است.

## ۱۰. هشدار درباره معماری پیشنهادی

پشته فناوری و معماری Modular Monolith با تصمیم `DEC-007` و `DEC-006` تأیید شده‌اند؛ با این حال جزئیات اجرایی و تصمیم‌های ماژول‌های بعدی همچنان قابل بازبینی‌اند. موارد زیر:

- تصمیم تأییدشده کاربر نیستند؛
- به‌معنای انتخاب قطعی فناوری یا شروع پیاده‌سازی نیستند؛
- ممکن است پس از بررسی تصمیم‌های باز (مانند روش احراز هویت و نیازهای مکانی) اصلاح شوند.

هیچ بخشی از این مخزن نباید بدون تأیید کاربر به‌عنوان مبنای پیاده‌سازی فاز بعدی تلقی شود.
